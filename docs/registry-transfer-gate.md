# 등록계 본계정 전환 승인 게이트 — 설계

> 관제탑 2026-08-18 지시(**설계만 · 구현 금지**)에 대한 회신.
> 수치는 실DB 직접 조회(2026-08-19). 이 문서는 **코드·DDL을 변경하지 않는다.**

---

## 1. 현행 — 전환에 승인자가 없다

`/등록계`(LESSON_GUILD 등록, `server.js:905`)의 현재 흐름:

```
/등록계 입력 → [확인] 버튼(자기신고) → runRegistryRegister()
   → PUBG 실존확인 → registry_history SCD-2 → clan_registry upsert  ← 즉시 확정
```

**게이트는 자기신고 버튼 하나뿐이다.** 이미 등록계가 있어도 `/등록계`를 다시 실행하면
그 자리에서 교체된다(`server.js:1605` — "이미 등록한 계정이 있으면 이 계정으로 **교체**돼").
`prev`가 있으면 `note='등록계 변경'`으로 이력만 남고, **승인·대기·거절 상태가 존재하지 않는다.**

### 1-1. `ownership_confirmed`는 「확인됨」이 아니라 「본인이 그렇게 말했다」이다

`server.js:1563`이 버튼 통과분에 `ownership_confirmed: true, confirmed_at`을 박는다.
필드 이름은 **명의 확인**인데 실제 내용은 **자기신고**다. 확인한 사람이 없다.

→ 이름과 내용이 어긋나 있어, 이 값을 근거로 「명의가 확인된 계정」이라고 읽으면 틀린다.
   **권고: `self_attested`(자기신고)와 `ownership_confirmed`(운영진 확인)를 분리한다.**
   기존 컬럼 개명은 파괴적이므로 새 컬럼 추가 + 기존 값은 자기신고로 이관하는 쪽이 안전하다.
   (DDL이므로 이 문서는 발행만 한다.)

## 2. 실측 — 전환은 이미 일어나고 있고, 성격이 균일하지 않다

`registry_history` 전량(시즌 42):

| note | 행 | 인원 | 기간 |
|---|---:|---:|---|
| 최초등록 | 47 | 39 | 07-25 ~ 07-30 |
| **등록계 변경** | **4** | **3** | 07-30 ~ 07-31 |

전환 3명의 궤적:

| 대상 | 이전 → 이후 | 플랫폼 | 비고 |
|---|---|---|---|
| A | `GmI_2muri` → `GmI_mriacademy` | steam → steam | 6일 간격 |
| **B** | `GmI_Soondae` → `HAM-CHEESE-TOAST` → `b_Soondae` | **steam → steam → kakao** | **하루에 3회** |
| C | `PineapplePxssy` → `GmI_MinChun` | steam → steam | 4일 간격 |

**두 가지가 드러난다.**

1. **플랫폼 교차 전환이 실재한다**(B: steam → kakao). 전적 파이프라인은 플랫폼별로
   shard·seasonId·accountId가 **전부 분리**된다(CLAUDE.md 「PUBG 전적 파이프라인」).
   즉 플랫폼 전환은 닉 변경과 성격이 다르다 — 이전 시즌 기록과의 연속성이 끊긴다.
2. **연속 교체에 제동이 없다**(B: 하루 3회, `valid_from`=`valid_to`인 0일 구간 발생).
   상한이 코드에 없으니 횟수 제한은 사실상 없다.

## 3. 왜 게이트가 필요한가 — 하류에서 조용히 뒤집힌다

`matchClanRegistry()`(`server.js:3751`)가 G드컵 팀 신청을 검증한다:

```js
const rows = await sbSelect("clan_registry", `select=pubg_name&season=eq.${PUBG_CUR_SEASON_NUM}`);
const known = new Set(rows.map((r) => String(r.pubg_name || "").trim().toLowerCase()));
const verified = members.map((m) => known.has(String(m.ign || "").trim().toLowerCase()));
```

대조 키가 **`pubg_name` 문자열**이다. 그래서 등록계를 바꾸는 순간:

> **이미 신청을 마친 팀의 `verified`가 소급해서 false로 뒤집힌다.**
> 차단이 아니라 경고만이라(설계상 의도) **아무도 그 시점을 모른다.**

신청 당시 통과했는지 여부가 어디에도 남지 않는다 — 대조가 **그때그때 현재값**으로만 이뤄지기 때문이다.

### 3-1. ⚠️ 트랙 경계 — G드컵 쪽 수정은 이 트랙이 하지 않는다

`matchClanRegistry`·`/api/gdcup-*`는 **카지노 트랙 소관**이다(CLAUDE.md 경계 규칙).
이 문서는 **문제 제기와 요구사항 전달까지**만 한다. 위 「소급 뒤집힘」의 해소책
(신청 시점 스냅샷 보존 = `gdcup_apps`에 대조 결과를 박아 두기)은 카지노 트랙에 요청한다.

**등록계 쪽(이 트랙)에서 할 수 있는 것은 전환 자체를 늦추는 것**이고, 그게 이 설계다.

## 4. 설계 — 전환만 승인 대상으로 가른다

### 4-1. 최초등록은 승인 대상이 아니다

39명 중 36명이 한 번 등록하고 끝이다. 최초등록까지 대기로 만들면 **신규 유입이 오너 응답
속도에 묶인다** — 얻는 것 없이 마찰만 는다. 게이트는 **전환에만** 건다.

### 4-2. 전환을 3등급으로 나눈다 — `account_id`가 판별축이다

`pubg_name`은 PUBG에서 바뀔 수 있고 `account_id`는 불변이다. 그래서 **닉 변경과 계정 교체는
account_id로 기계적으로 갈린다** — 사람 판단이 필요 없는 구간이 존재한다.

| 등급 | 조건 | 처리 |
|---|---|---|
| **T0 자동 허용** | `account_id` 동일 · `pubg_name`만 변경 | 즉시 반영. PUBG 닉 변경이라 승인 불요 |
| **T1 승인 필요** | `account_id` 변경 · 플랫폼 동일 | 대기 → 오너 승인/반려 |
| **T2 승인 + 사유 필수** | **플랫폼 교차** | 대기 → 사유 입력 필수 → 오너 승인/반려 |

T0을 자동으로 두는 것이 중요하다 — 닉 변경까지 승인 대기로 만들면 **정당한 사용자가 가장
자주 겪는 경우가 가장 느려진다.**

### 4-3. 쿨다운 — 실측이 근거다

B의 하루 3회가 실제 사례다. 두 축을 함께 건다(한쪽만으로는 못 막는다):

- **시즌당 전환 상한** — 승인된 T1·T2 전환 기준(T0 닉 변경은 세지 않는다)
- **직전 전환 후 최소 경과일**

구체 수치(상한 N회 · 경과 D일)는 **운영 정책이라 오너가 정한다.** 코드가 임의로 못 박지 않는다.

### 4-4. 승인 큐는 새로 만들지 않는다 — §18 패턴 재사용

`payment_requests`(§18)가 이미 **대기 → 오너 DM 버튼 → 승인/반려** 구조를 갖고 있고
`/결제신청`이 그 경로로 돈다. 등록계 전환도 같은 모양이므로 **구조를 복제하지 말고 같은 패턴을
따른다**(테이블은 별개, 흐름은 동일).

필요한 상태: `pending` / `approved` / `rejected` / `expired`.
`expired`가 있어야 오너가 응답하지 않은 신청이 영구 대기로 남지 않는다.

### 4-5. 대기 중 표시 — 「전환 신청 중」이 보여야 한다

전환이 대기 상태로 들어가면 **현재 등록계는 이전 계정 그대로**다. 이걸 표시하지 않으면
신청자는 바뀐 줄 알고 그 닉으로 G드컵에 신청한다 → `matchClanRegistry` 미등록 경고가 뜬다.

→ `/등록계현황`(오너 DM, `server.js:1994`)에 **대기 건 섹션**을 추가하고,
   신청자 본인에게는 신청 접수 응답에 「승인 전까지 기존 등록계가 유효하다」를 명시한다.

## 5. 필요한 스키마 (발행만 — 실행은 오너)

이 설계를 구현하려면 아래가 필요하다. **DDL은 승인 후 별도 PR에서 발행한다** —
지금 붙이면 쓰는 코드가 없어 `REQUIRED_SCHEMA` 사각지대만 는다.

| 대상 | 내용 | 이유 |
|---|---|---|
| 신규 테이블 `registry_transfer_requests` | discord_id · season · from/to(platform·pubg_name·account_id) · tier(T1/T2) · reason · status · 신청/판정 시각 · 판정자 | 승인 큐 |
| `clan_registry.self_attested` | boolean | `ownership_confirmed`의 실제 의미(자기신고)를 분리 |
| `registry_history.note` | 값 확장 (`전환승인`·`전환반려`·`닉변경`) | 지금은 `최초등록`/`등록계 변경` 2종뿐이라 T0/T1/T2가 구분되지 않는다 |

⚠️ `note`는 자유 텍스트 컬럼이라 **CHECK가 없다** — 값 확장에 DDL이 필요 없는 대신
**오타가 조용히 통과한다.** 값 목록을 코드 상수로 고정하고 그 상수만 쓰게 한다.

## 6. 이 설계가 풀지 못하는 것 (명시)

- **명의 진위 자체는 여전히 확인 못 한다.** 승인 게이트는 「오너가 봤다」를 보장할 뿐
  계정이 실제 본인 것인지는 증빙 없이 알 수 없다. 증빙 절차는 이 설계 범위 밖이다.
- **이미 신청된 G드컵 팀의 소급 뒤집힘**은 등록계 쪽에서 못 막는다(§3-1). 카지노 트랙 과제다.
- **시즌 경계**: `prev` 조회가 `season` 단위라 시즌이 바뀌면 전환이 아니라 최초등록이 된다.
  시즌 간 계정 연속성을 볼지는 **정책 판단**이라 오너 결정이 필요하다.
  (실측 47 최초등록 / 39명의 차이 8건이 이 경로일 수 있다 — 시즌 42 단일이라 현재는 미발생.)

## 7. 오너 판정이 필요한 항목

1. 전환 상한 **N회/시즌** · 최소 경과 **D일** (§4-3)
2. T2(플랫폼 교차)를 **허용할지 자체**를 막을지 — 막으면 승인 큐가 T1만 다룬다
3. `ownership_confirmed` 분리 방식 — 새 컬럼 추가 vs 기존 값 의미 재정의 (§1-1)
4. 시즌 경계에서 전환 이력을 이어 볼지 (§6)
