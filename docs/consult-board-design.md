# 상담 보드 — 레벨 테스트 · 클랜 상담 · 일반 상담을 한 화면으로 (설계 · 2026-10-01)

> **오너 방향(10/1 · 어플 전달)**: 디코 상담 기록 채널(담당 · 대상자 · 유형 · 일정 · 시간 · 진행 상태 · 입금 상태 · 메모 양식)을
> 앱에서 보기 좋게. 신청 창구(`intake_applications` · `intake_cards`)와 상담 기록(`consults`)을 한 흐름으로 —
> 신청 → 시간 잡힘 → 입금 확인(유료만) → 끝남 → 결과(등록 · 고민 중 · 안 함). **기존 consults · 상담 가산 정산은 그대로(바뀌는 계산 없음).**
> 계약은 `docs/trainer-portal-api.md` §9.23 이 정본이다. 이 문서는 왜 그렇게 했는지를 적는다.

## 0. 한 줄

**보드의 카드 한 장 = 상담 한 건.** 카드는 세 곳에서 온다 — 상담 기록(`consults` 행) · 레벨 테스트 예약(`slot_bookings` · 상담 칸) ·
아직 칸을 못 잡은 신청(`intake_applications`). 앱은 셋을 구분하지 않고 카드 `id` 하나로 부른다. 카드에 메모 · 결과 · 넘김을 처음 적는 순간
서버가 그 카드의 `consults` 행을 만들어 붙인다(예약 · 신청과 짝). 레벨 테스트 「완료」는 지금처럼 상담 기록을 남기되, 이미 붙은 행이 있으면
**새로 만들지 않고 그 행을 채운다.**

## 1. 지금 있는 것 (실측 10/1)

| 것 | 지금 | 보드에서 |

| 레벨 테스트 칸 | `trainer_slots.lesson_type='consult'` · 예약 = `slot_bookings` | 시간 잡힌 카드 |
| 신청 창구 | `intake_applications`(new → claimed → booked → paid → tested → enrolled · closed) · 트레이너 라우트 §9.20 · 10/8 접수 시작 | 신청 단계 카드 · 맡기 · 칸 넣기 · 등록은 §9.20 을 그대로 부른다 |

| 상담 가산(정산) | **`payments`(kind consult · handler_id)로 센다** — `consults` 를 보지 않는다(admin-panel.js) | **손대지 않는다.** 보드는 결제 행을 만들거나 고치지 않는다 |
| 디코 상담 기록 채널 | 양식 메시지(오너 예시 14건 · 8/22~9/24) | §6 옮기기(드라이런 먼저) |

## 2. 유형 · 단계 · 결과

- **유형** `type`: `level_test`(레벨 테스트 · 유료 · 정가 `PRICES.consultCourse`) · `clan`(클랜 상담 · GmI · 무료) · `general`(일반 상담 · 무료).
  DB 는 새 칸 `consults.consult_type`. 칸이 비어 있는 옛 행은 `kind` 로 읽는다 — `consult` → `level_test` · `clan` → `clan`.
  (`kind` 는 그대로 둔다 — 봇 · 사이트 신청 · 정산 문서가 쓰는 값이다. 일반 상담도 `kind='consult'` 에 `consult_type='general'`.)
- **단계** `stage`: `applied`(신청 · 시간 전) → `scheduled`(시간 잡힘) → `done`(끝남) · 어느 단계든 `closed`(취소 · 노쇼 · 신청 닫음).
- **입금** `deposit`: 무료면 `none` · 유료면 `waiting` → `confirmed` · `refunded`. **보드에서 바꾸지 않는다**(읽기만) —
  신청은 §9.20 [입금 확인], 그 밖은 지금처럼 입금 신청 · `/결제신청`(구분 상담)이 결제를 만들고, 레벨 테스트 「완료」가 결제를 상담 기록에 붙인다.
- **결과** `result`: `enrolled`(등록) · `thinking`(고민 중) · `declined`(안 함) · 비어 있음. 「고민 중」 3일이 지나면 담당 트레이너에게 DM 한 번.

## 3. 데이터 — §60 (더하기만 · A 구간)

`consults` 에 칸을 더한다. 기존 칸 · 제약 · 데이터는 그대로다.

| 칸 | 뜻 |
|---|---|
| `consult_type` | `level_test` · `clan` · `general`(check) |
| `booking_id` | 레벨 테스트 예약(`slot_bookings`) — **한 예약에 한 행**(부분 유니크) |
| `application_id` | 신청(`intake_applications`) |
| `outcome` · `outcome_note` · `outcome_at` · `outcome_by` | 결과(check 3값) · 결과 메모(500자) · 정한 시각 · 누가 |
| `thinking_reminded_at` | 「고민 중」 3일 DM 을 보낸 시각(한 번만 · 결과를 다시 고민 중으로 정하면 비운다) |
| `handover_at` · `handover_note` | 넘긴 시각 · 넘길 때 한 줄 |
| `updated_at` | 마지막으로 바꾼 시각 |

인덱스: `channel_msg_id` 부분 유니크(디코 옮기기 중복 막기) · `booking_id` 부분 유니크 · `application_id` · 「고민 중」 DM 대상 부분 인덱스.
`REQUIRED_SCHEMA.consults` 에 새 칸을 더한다(3곳 동기).

## 4. 흐름별로 바뀌는 것

| 흐름 | 바뀌는 것 |
|---|---|
| 신청 → 맡기 → 칸 넣기 → 입금 확인 → 마침 → 등록 · 닫기 | **없음**(§9.20 그대로). 보드는 신청 · 예약을 읽어 카드로 보여 준다 |
| 레벨 테스트 「완료」(`consult-record.cjs`) | 그 예약의 `consults` 행이 있으면 **그 행을 채운다**(done · 진행자 · 금액 · 결제 연결) · 없으면 지금처럼 만든다(`booking_id` · `application_id` 를 같이 적는다). 결제 연결 규칙(±45일 · 딱 한 건)은 그대로 |
| 보드에서 메모 · 결과 · 넘김 · 명부 연결 | 그 카드에 `consults` 행이 없으면(예약 · 신청 카드) 먼저 만들어 붙인다 — 같은 예약에 두 행이 생기지 않게 유니크가 막는다 |
| 보드에서 직접 만든 상담(클랜 · 일반 · 칸 없는 레벨 테스트) | `consults` 새 행(`source` 비움 · `registered_by='staff:<id>'`) |
| 「등록하기」 | 신청 카드 → §9.20 등록(같은 함수) · 그 밖 → 명부 연결된 사람을 prospect → active · 레벨 · 담당(넘김 받은 트레이너 먼저). 디스코드가 명부에 있으면 앱이 바로 열린다 |

## 5. 권한 · 개인정보

- 원장: 전부. 트레이너: 내가 담당 · 진행 · 넘겨받은 카드 + 내 상담 칸 예약 + 신청 목록 규칙(§9.20.2)과 같은 신청.
- 신청 단계의 실명 · 나이는 지금처럼 **원장 전용**(`ownerView`). 트레이너에게는 디스코드 표시 이름이 간다.
- 전화번호 · 계좌 · 금액 · 결제 키는 응답에 없다(트레이너 가드가 막는다). 메모는 `note` 키로 내린다(가드가 `memo` 어간을 막는다).
- 결과 메모 · 넘김 한 줄은 사람이 쓰는 글이라 로그에 남기지 않는다(코드와 건수만).

## 6. 디코 상담 기록 옮기기 — 피드백 이관과 같은 방식

1. **채널 링크(또는 id)를 오너에게 받는다** — 지금 스캔(피드백 이관 때 3서버)에는 상담 기록 채널이 없다(GmI 서버는 그때 건너뛰었다).
2. 드라이런: 봇이 채널 메시지를 읽어 양식을 푼다(담당 · 대상자 · 유형 · 일정 · 시간 · 진행 상태 · 입금 상태 · 메모 — 띄어쓰기 · 콜론 모양이 달라도 읽는다).
   - 대상자 → 명부 짝(이름 · 별칭 · 배그 닉 · 디스코드 멘션이면 그 계정). 동명이인 · 짝 없음 · 애매는 따로 센다.
   - 유형 → `클랜` 이 들어가면 `clan` · `레벨` · `진단` 이면 `level_test` · 그냥 「상담」은 입금 상태(금액 · 입금 완료)가 있으면 `level_test` 아니면 `general`.
   - 이미 있는 `consults` 행(같은 사람 · 같은 날 ±1일)과 겹치면 새로 만들지 않고 **짝으로만** 보고한다(기존 행은 고치지 않는다).
   - 결과는 `ops_state` 에 건수와 메시지별 판정(이름 없이 #번호)으로 남긴다. 쓰기 0.
3. 오너가 드라이런을 보고 OK → 쓰기(**B 구간 · 이관 대량 쓰기**): 새 `consults` 행(`source='discord'` · `channel_msg_id`) +
   짝 없는 대상자는 prospect 명부(오너가 「만들기」로 고른 것만). 원본 메시지 id 유니크라 두 번 돌려도 두 번 안 들어간다.
4. 옮긴 뒤 채널 운영(잠금 · 고정 메시지)은 오너가 정한다 — 피드백 이관 때와 같다.

## 7. 숫자 · 알림

- `GET /consults/stats?month=` — 월별 · 트레이너별 끝난 상담 · 등록 · 고민 중 · 안 함 · **등록 전환율 = 등록 ÷ 끝난 상담**. 유형별 건수.
  기준 월 = 끝난 시각 → 없으면 잡힌 시각 → 없으면 등록일(KST). 트레이너 = 진행자 → 없으면 담당.
- 「고민 중」 3일: 10분 점검이 `outcome='thinking'` 이고 정한 지 72시간 지난 카드를 찾아 **넘겨받은 트레이너 → 담당 → 진행자** 순으로 한 명에게 DM 한 번.

## 9. 오너 확인

1. 상담 기록 채널 링크(또는 id) — 옮기기 드라이런에 필요하다.
2. 디코 양식의 그냥 「상담」이 유료 레벨 테스트인지 일반 상담인지 — 드라이런은 입금 상태로 가르고 결과표에 그 판정을 보여 준다.
3. 유료 상담의 [입금 확인]을 보드에서도 누르게 할지(지금은 신청만 원장 카드 [입금 확인] · 그 밖은 입금 신청 · `/결제신청`) — 결제 데이터를 만드는 일이라 결제 트랙 확인 뒤.
4. 담당이 비어 있는 상담(디코에서 옮긴 것 · 사이트 신청)을 트레이너에게도 보일지 — 이 설계는 **원장만 보고 원장이 담당을 정한다.**
