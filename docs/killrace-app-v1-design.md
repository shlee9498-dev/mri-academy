### §0.5 지금 방식이 2천 명에서 막히는 곳

1. **회차가 코드에 박혀 있다** — 신청 회차 · 정원 · 마감이 상수라 회차마다 배포한다.
2. **본인 확인이 느슨하다** — 「내 신청」은 디스코드 닉 + 스팀 닉이 맞으면 열린다. 둘 다 남이 볼 수 있는 값이라 남의 소개를 고칠 수 있다.
3. **참가 구분을 본인이 고른다** — 레슨생 · 클랜원 · 외부를 본인이 고르고 진행자가 손으로 확인한다.
4. **명부가 없다** — 신청 명단은 회차마다 `ops_state` 한 줄(JSON)이다. 회차 20명엔 충분하지만 회원 2천 명을 담을 자리가 아니다.
5. **계좌를 모든 신청자에게 받는다** — 상금을 못 받은 사람의 계좌까지 쌓인다.
6. **진행자 권한이 키 하나다** — 누가 눌렀는지는 진행자가 적는 이름(`by`)뿐이다.
7. **신청 때마다 PUBG 조회** — 기본 분당 10번 한도라 공지 직후 몰리면 막힌다.
8. **동의 줄이 없다** — 신청서가 계좌(은행 · 번호 · 예금주)를 받는데 목적 · 보관 기간 · 누가 보는지를 적은 동의 줄이 없다.
   G드컵 S3 신청서에는 있다(「실명·계좌는 상금 지급 목적으로만 수집·이용하며 대회 정산 종료 후 파기합니다」). 받은 계좌 줄(`applypay:r2`)을 지우는 날도 정해져 있지 않다.
   v1 을 기다리지 않고 지금 신청서에 한 줄 넣을지는 지휘 판단이다(이 문서는 화면을 고치지 않았다).

### §1.1 새 API 모양 (초안 · 숫자는 서버 값만 · 점수식은 읽기만)

- **`GET /api/killrace/events`** — 지금 칸(`currentId` · `events[{ id, name, start, end }]`)은 그대로 두고, 회차마다 `status`(`upcoming` · `live` · `ended`) · `cap` · `applied` · `waiting` · `closeAt` 을 더한다.
  앞날 회차 = `event_defs` 에서 시작이 아직 안 온 줄.
- **`GET /api/killrace/rules?event=N`** — `{ event, teamSize, cap, score{ chicken, damagePer, slotPenalty, leave }, boost{ mode, seqs, mul }, lateRevive{ rule, phase }, auction{ budget, startPrice, bonusPer, negativeMul, tierBonus } }`.
  지금 코드 상수와 `killrace:event:<id>` 설정을 **읽어서 보여 주기만** 한다. 룰이 바뀌어도 앱을 안 고친다(#103 요청 3).
- **`GET /api/killrace/career/:key`** — `{ key, ign, games, kills, damage, deaths, killsPerGame, damagePerGame, teamTopKills, sample, events[{ id, name, team, games, kills, damage }] }`.
  `key` 는 계약 §1.11 불투명 키 그대로다(계정 번호를 되찾을 수 없다).
- **`GET /api/killrace/me`**(로그인) — `{ linked, platform, ign, key, kind, applications[{ event, status, order, introDone }], consent{ version, at } }`.
  디스코드 번호 · 계정 번호는 본인 것이라도 싣지 않는다.
- **`POST /api/killrace/me/link { ign }`** — 서버가 PUBG 에서 닉을 찾아 **계정 번호로 고정**한다(계약 §1.1 `pickPlayer` 규칙). 같은 계정은 회원 한 명에게만 — 이미 다른 회원이 연결했으면 409 `account_taken`(진행자가 푼다).
  조회는 줄을 세워 분당 한도 안에서 돈다. 몰리면 「확인 중」으로 받고, 끝나면 화면이 다시 읽는다.
- **`POST /api/killrace/me/apply { event }`** → `{ state: "joined" | "waiting", order }` — 연결된 계정으로 신청. 정원 · 마감은 **회차 설정**에서 읽는다. 같은 계정은 회차에 한 번.
- **`POST /api/killrace/me/cancel { event }`** — 취소하면 대기 맨 앞이 올라온다(지금 규칙 그대로).
- **`POST /api/killrace/me/intro { event, intro }`** — 소개 4칸(계약 §1.15 규칙 그대로).
- **`POST /api/killrace/me/leave`** — 탈퇴(§5.3).
- 실패는 `{ error: { code } }` 모양(지금과 같다). 로그에는 건수 · 단계만 남긴다.

### §1.2 저장 (DDL 초안은 구현 주문 때 · 더하기만)

| 표(이름은 구현 때) | 칸 | 누가 봄 |
|---|---|---|
| 회원 | 디스코드 번호(유일) · 표시 이름 · 플랫폼 · PUBG 계정 번호(유일) · 닉 · 연결 시각 · 동의 버전 · 동의 시각 · 마지막 로그인 · 탈퇴 시각 | 서버 · 오너(진행자는 닉 · 구분까지) |
| 신청 | 회차(`event_defs` 외래 키) · 회원 · 상태(참가 · 대기 · 취소) · 신청 시각 · 취소 시각 · 소개 4칸 · 구분 · 참가비 확인 | 공개(닉 · 소개 · 상태) · 진행자(구분 · 참가비) |
| 상금 계좌 | 회원 · 은행 · 번호 · 예금주 · 받은 시각 · 지울 날 | **오너만** |

- 계좌는 회원 · 신청과 **다른 표**에 둔다 — 지금 `applypay` 를 따로 둔 것과 같은 까닭이다(공개 · 진행자 응답이 그 표를 열지 않는다).
- 회차 정원 · 마감 · 참가비는 회차 설정으로 옮긴다(`killrace:event:<id>` 또는 `event_defs` 새 칸) — 회차마다 배포하지 않는다.
- `clan_registry`(등록계)는 실명 칸이 있어 그대로 쓰지 않는다. 같은 디스코드 번호로 서버 안에서만 대조한다(「등록계 있음」 표시만).
- 지금 웹 신청(`killnaegi.html` · `killrace:apply:r2`)은 v1 이 열리기 전 회차까지 그대로 둔다. 한 회차를 두 길로 받지 않는다.

## §2 로그인

### §2.1 디스코드 로그인은 다시 쓸 수 있다

- 사이트 로그인은 돌아갈 주소가 `ALLOWED` 출처면 받고(`safeReturn`), 그 목록에 `shlee9498-dev.github.io` 가 있다.
  → **gmi-clancup Pages 화면이 지금 로그인을 그대로 쓴다. 새 env · 새 redirect URI 가 없다.** CORS 도 같은 목록이라 화면이 API 를 바로 부른다.
- 수강생 앱 세션(포털 `/exchange`)은 **수강생 명부에 있어야** 열린다 → 클랜원 2천 명에게 맞지 않는다(#103 문서 §3 「입구」).
- 카지노 앱 로그인은 다른 서버 · 다른 서명 키 · 휴면 트랙이고, 카지노와 잇지 않는다는 주문(§4)과도 맞지 않는다 → 쓰지 않는다.
- **구현 때 고칠 것 셋**
  1. **킬내기 표지** — `intent=killrace` 로 로그인하면 토큰에 `aud: "killrace"` 를 싣고 기간을 짧게 둔다(제안 7일). 킬내기 `/me` 길은 이 표지만 받는다.
  2. **사이트 쪽은 이 표지를 거절** — `github.io` 출처는 오너 저장소 Pages 전부가 같은 브라우저 저장소를 쓴다(카지노 앱 토큰도 같은 출처).
     운영진이 킬내기 앱에 로그인해도 그 토큰으로 패널 · 운영진 권한이 열리면 안 된다 → `getUser` 가 `aud` 있는 토큰을 받지 않게 한다. 지금 토큰(표지 없음)은 그대로 돈다.
  3. **로그인 CSRF** — 신청 창구(`intent=apply`)처럼 nonce 를 싣는다(`intake-api.cjs` 모양을 다시 쓴다).
- 디스코드 동의 화면에는 **사이트 로그인용 디스코드 앱(MRI) 이름**이 뜬다. GmI 이름으로 띄우려면 GmI 쪽 디스코드 앱을 써야 하고,
  그러면 client id · secret · redirect URI 가 새로 든다(오너 손 · §6 2번).

### §2.2 디스코드 닉 + 스팀 닉 확인을 무엇으로 바꾸나

| 지금 | v1 |
|---|---|
| 사람 = 디스코드 닉(본인이 적음) | 사람 = **디스코드 계정 번호**(로그인이 증명 · 서버 안에만 둔다) |
| 스팀 = 닉(신청 때마다 조회) | 스팀 = **PUBG 계정 번호**(연결 때 한 번 조회 · 닉이 바뀌어도 이어진다) |
| 「내 신청」 = 두 닉이 맞으면 열림 | 「내 신청」 = 로그인한 본인 것만 |
| 구분 = 본인이 고름 → 진행자 손 확인 | 구분 = **서버가 정함**(아래) → 판정 못 하면 지금 방식으로 |
| 닉만 다르면 한 계정으로 여러 번 신청 가능 | 계정 번호 하나 = 회원 하나 |

- **참가 구분 자동 판정** — 레슨생 = 활성 수강생 중 `students.discord_id` 가 같은 사람 · 클랜원 = GmI 길드 회원 + 클랜원 기준(§6 3번 · 봇이 GmI 길드에 있어 한 사람씩 조회한다 · 구현 때 실측) · 그 밖 = 외부(참가비 안내).
  화면에는 구분 이름만 나가고 대조 근거는 나가지 않는다. 봇 조회가 실패하면 지금처럼 본인 선택 + 진행자 확인으로 떨어진다.
- **스팀 계정 주인 확인은 v1 에서 조회만 한다.** PUBG 공개 API 로는 계정 주인을 증명할 길이 마땅치 않다 — 스팀 로그인(OpenID)은 스팀 계정만 증명하고,
  우리가 쓰는 PUBG 응답 칸에는 스팀 번호가 없다(둘을 잇는 값이 있는지는 v2 전에 실측). 대신
  ① 계정 번호 하나에 회원 하나 ② 남이 먼저 연결했으면 진행자에게 알려 해제 ③ 연결 · 바꾸기 이력을 남긴다.
  등록계(`/등록계`)도 기술 증명이 아니라 본인 확인 버튼 + 승인 방식이다.
- **지난 기록은 저절로 이어진다** — 개인 기록이 이미 계정 번호로 쌓여 있어(계약 §1.8 · §1.11) 스팀을 연결하는 순간 2 · 3 · 4회 기록이 내 기록으로 보인다. 옛 신청 줄을 옮길 필요가 없다.

## §8 자율 판 — 오너 없이 굴러가는 기본 판 (10/8 · 오너 방향 · 지휘 기본값)

> 오너(10/8 새벽): 「경매는 굳이 기본으로 안 둬도 돼 내가 없이 킬내기판이 자율적으로 진행되려면 경매없이도 돼야하겠지 대승배니까 경매를 한거야 판단대로 해봐 노래방룰을 기본으로 하면 좋긴할듯」
>
> **기본 판 = 자율 판**(점수 상한제 편성 · 노래방 룰). **경매 = 대승배 같은 행사 때만 쓰는 특별 모드**(§4 2단계 범위 그대로).
> 이 절은 설계만이다 — 구현은 1단계 서버 조각(§7) 뒤 2단계에서 한다. 오늘 대승배(경매 · 기존 룰)와 기존 회차 기록은 건드리지 않는다.

### §8.1 흐름

| 단계 | 누가 | 무엇 |
|---|---|---|
| 판 열기 | 로그인한 **GmI 길드 가입자**(계약 §5 의 길드 조회 그대로) · **하루 한 사람 1판** | 시작 · 종료 시각(노래방 룰 창 · §8.2) · 팀 수 · 팀 인원(2 ~ 4) · 편성 방식((가) 자동 균형 / (나) 팀장 고르기) · 참가 마감. **진행자 키 없음** |
| 참가 | 로그인 + 스팀 연결된 회원(계약 §4.2) | 「참가」 한 번. 닉 · 계정은 대조표(계약 §4.5)에서 자동 · 정원(팀 수 × 팀 인원)을 넘으면 대기 |
| 편성 | 서버(가) 또는 팀장(나) | 참가 마감에 편성 → 팀 등록(지금 `event_teams` 와 같은 모양 · 슬롯 = 점수 높은 순) |
| 집계 | 서버 | **지금 자동 집계 그대로**(1분마다 · 열린 대회 여럿 동시 · killrace-api §1.6) |
| 닫기 · 결과 | 서버 | 창 끝 + 45분에 자동으로 닫히고 결과가 남는다(지금 회차와 같다 · 판을 연 사람이 없어도 된다) |
| 기록 | 서버 | 개인 누적 기록 · 티어표에 쌓인다. 정식 회차와 **구분값 「약식」**(§8.5) |

### §8.2 노래방 룰 (기본)

- 정한 시간 창 [시작, 종료) 안에 **시작한 판만** 인정한다 — 끝이 창을 넘어도 인정(10/7 번외 「01:00 전에 시작한 판은 인정」과 같다). 판 수 제한은 따로 없다(창이 곧 판 수).
- 버닝 · 늦은 부활 같은 회차 룰은 **지금 코드의 기본값 그대로**다. 판을 연 사람이 바꾸지 않는다(룰은 `GET /rules?event=` 로 누구나 본다 · 계약 §8.2).

### §8.3 선수 점수와 점수 상한제 (기본 편성)

- **선수 점수(0 ~ 100) = 판당 킬 50 + 판당 딜 50** — 개인 누적 기록(계약 §8.3)에서 **10판 이상 선수들 사이 백분위**로 환산한다
  (판당 킬 백분위 × 50 + 판당 딜 백분위 × 50). **10판 미만 · 첫 출전은 가운데 값(50)** 으로 시작한다. 점수식(판 점수)은 바꾸지 않는다 — 편성에만 쓴다.
- **팀 상한** = 참가자 점수 합 ÷ 팀 수 × 1.1 (올림) — 자동 계산(§8.9 5번 · 경비 제안). 어느 편성이든 팀 합계가 상한을 넘지 않는다.
- **(가) 자동 균형**: 서버가 팀 합계 차이가 가장 작게 나눈다 — 점수 높은 순 지그재그 배정 → 두 팀 사이 한 명씩 맞바꿔 차이를 줄인다. 같은 참가자면 같은 결과(재현 가능).
- **(나) 팀장 고르기**: 팀장 = 점수 상위 팀 수만큼(또는 판을 연 사람이 지정) · 고르는 순서 지그재그(1 → N, N → 1) · 차례마다 **타이머 30초 · 1분 · 2분**(판을 연 사람이 고름).
  상한을 넘기는 사람은 고를 수 없다(회색). 시간이 지나면 상한 안에서 남은 사람 중 점수가 가장 높은 사람을 자동으로 넣는다. 아무도 상한에 안 맞으면 점수가 가장 낮은 사람.
- **경매 전용 룰(남은 포인트 가산 · 티어 가산)은 쓰지 않는다** — 자율 판의 시작 점수는 모두 0.

### §8.4 돈 · 보상

- 자율 판에는 **상금 · 코인 · 보증금을 붙이지 않는다**(기록만). 계좌(계약 §7) · 결제 · 상금 장부(#520)와 잇지 않는다.

### §8.5 기록과 구분

- 회차 설정(`ops_state` `killrace:event:<id>`)에 `kind: "casual"`(약식) · 정식 회차는 지금처럼 비워 둔다(= official). **DDL 없이** 간다.
- 개인 누적 기록 · 티어표에는 같이 쌓되, 응답(계약 §8.3 `byEvent`)에 구분을 실어 화면이 「정식만 / 전부」로 거를 수 있게 한다.
- **「지금 대회」(가장 큰 번호)는 정식 회차만 본다** — 오버레이 · 점수판 · `/킬내기팀등록` · 경매의 기본 회차가 자율 판에 끌려가지 않게(10/7 번외 때 이 문제가 실제로 생길 뻔했다).
  자율 판 화면 · 오버레이는 판 번호로 연다(`?event=`).
- 자율 판 이름은 「약식 · <연 사람 스팀 닉> · 10/9 21:00」 모양 · 회차 글자는 「약식」(gmi-clancup #100 의 「번외」 규칙에 한 줄 더한다).

### §8.6 자율이라서 막아 둘 것

- 하루 한 사람 1판 · **동시에 열린 자율 판 3개까지**(경비 제안) — 집계가 PUBG 분당 10번을 다른 기능과 나눠 쓴다(지금 한 차례에 열린 대회 5개까지 센다 · §0.5).
- 마감 때 참가자가 팀 2개를 못 채우면 자동 취소. 판을 연 사람은 **시작 전에만** 취소할 수 있다(시작 뒤에는 기록 보존).
- 판을 연 사람이 사라져도 편성 · 집계 · 닫기는 서버가 끝까지 한다.
- 문제가 생기면 진행자가 지금 도구(진행자 키 · 판 무효 · 선수 빼기)로 정식 회차와 똑같이 손본다.

### §8.7 화면 참고 (기능만 · 모양은 우리 디자인 · 계약 §10 킬내기 라이트 토큰)

- 대기자를 점수 구간별로 묶어 보여 주기(팀장 고르기 화면).
- 방송용 작은 오버레이 — 내 팀 선수별 점수 + 팀별 점유율 %(팀 점수 ÷ 전체 합).
