## 0. 요약

| 질문 | 결론 |
|---|---|
| enrollment 단위 | **결제 트랜치의 계약 승격 — 구매 1건 = 등록 1행.** '추가결제'는 갱신이 아니라 새 행 |
| 수량·금액 정본 | 수량(계약 판수) = `lesson_enrollments.games_total` · 금액 = `payments` 행(귀속: `lesson_enrollment_id`) |
| 환불 | **상계 금지.** `status='refunded'` + 음수 `payments` 행. 시트는 이미 이 모델이고 DB가 어긋나 있다(§3) |
| settlements | (period × trainer) 확정 1행. 도장(`settled_period`)의 회차 객체화 + 승인 감사 |
| 강의와의 관계 | `courses`와 대칭. `payments`는 `num_nonnulls(course_id, lesson_enrollment_id) <= 1`로 양다리 차단 |

## 1. 왜 트랜치 = 등록인가

정산 엔진이 이미 이 모델로 동작한다. `computeStudent`는 첫 결제 판수(`firstGames`)를
base 요율 경계로 잡고 이후 트랜치를 재결제(+5%p)로 본다 — 트랜치가 곧 요율 단위다.
등록을 트랜치보다 굵게 잡으면(사람당 1행) 이 경계를 다시 파생해야 하고, 가늘게 잡을
방법은 없다(트랜치가 최소 구매 단위다).

`결제_원장`의 `차수` 열('1차'·'추가'·'전환'·'환불')이 같은 구분을 이미 수기로 하고
있다. 장익교 7/11 행의 비고 *"33판 추가결제 → 레슨로그 결제금액·판수 갱신"* 처럼
시트는 추가결제를 **기존 행 갱신**으로 흡수하는데, 그 갱신이 정확히 이력을 지우는
지점이다 — 등록이 행으로 분리되면 갱신 자체가 없어진다.

`courses`(§17)와도 대칭이 맞는다: *"같은 사람이 재등록하면 행이 2개다(허혜민 사례)"*.

**분할납부는 등록 1행에 payments N행**이다. 등록:결제가 1:1로 고정되지 않는 이유이고,
환불 음수 행도 같은 등록을 가리키므로 자연스럽게 N:1이 된다.

## 2. 저장 수량 — `games_total`은 저장한다

강의 모델(§4)은 "저장 수량은 units 하나, 나머지 전부 파생"인데 레슨은 한 곳이 다르다.
계약 판수를 `Σ payments.games`로 파생하면 **부분 환불이 수량을 오염시킨다** —
백진환 건(아래 §3)처럼 돈만 일부 돌려주고 판수는 그대로인 경우, 음수 행에 games를
얼마로 적어도 어긋난다(0이면 금액과 안 맞고, 음수면 계약 판수가 줄어든 게 된다).
계약 수량은 **합의의 사실**이라 등록 행에 고정하고, 돈의 사실은 payments 행에 남긴다.
둘이 어긋나는 게 보이는 상태가 정상이다(그게 미수·환불이다).

소진·잔여는 전부 파생: `잔여 = games_total − Σ lesson_sessions.games (해당 등록 귀속)`.

## 3. 환불 표현 — 시트가 맞고 DB가 어긋나 있다

`결제_원장`은 환불을 음수 행으로 남긴다. 실측(7월):

```
07-10 김준길 판수 +80,000 → 07-12 환불 -80,000   (전액 환불, 행 2개 보존)
07-25 이지운 판수 +40,000 → 07-25 환불 -40,000   (당일 전액 환불)
07-25 백진환 판수 +130,000 → 07-29 환불 -10,000  (부분 환불)
```

DB `payments`는 백진환을 **07-25 · 120,000 한 행으로 상계**해 갖고 있다(7월 대조에서
"시트에 없는 DB 행"으로 걸린 5건 중 1건이 이것이다 — 130,000과 매칭 실패).
상계는 환불 사실 자체를 지운다: 언제·얼마를 돌려줬는지가 어디에도 없다.

→ **규칙: DB도 음수 행으로 통일한다.** 환불 = 음수 `payments` 행 + 같은
`lesson_enrollment_id` 귀속 (+ 전액 환불이면 등록 `status='refunded'`).
기존 상계 행(백진환 등)은 백필 대사에서 원장 기준으로 정정한다 — 시드가 아니라
대사 단계 항목인 이유는, 정정이 금액 변경(Level 0)이라 오너 승인 절차를 타기 때문이다.

이관 대사의 중복키는 `입금일|이름|금액`(#173에서 확정) — 상계 행은 이 키가 원장과
어긋나므로 대사가 자동으로 특정해 준다.

## 4. settlements — 도장의 회차 객체화

정산 동결의 실질 메커니즘은 `lesson_sessions.settled_period/settled_rate` 도장이다
(엔진은 도장 찍힌 세션을 재계산에서 제외). 그런데 두 가지가 비어 있었다:

1. **도장 컬럼이 정본 SQL에 없었다.** 실DB와 `REQUIRED_SCHEMA`에는 있는데
   `supabase_admin_panel.sql`에 빠져 있었다 — 3곳 규칙의 1번이 뚫린 상태.
   §19a가 멱등 보정한다(실DB에서는 no-op).
2. **"회차"라는 객체가 없다.** 어떤 달을 누구에게 몇 판·얼마로 확정했는지가 세션
   도장에 흩어져 있고, 확정 행위 자체(누가·언제)는 어디에도 안 남는다.

`settlements` 1행 = (period × trainer) 확정 1건. `draft`(엔진 산출 동결) →
`confirmed`(오너 확정, 이때 세션 도장 스탬프) → `paid`(`payout_id` 연결).
`unique (period, trainer_id)`가 같은 달 이중 확정을 구조적으로 막는다.

정산 확정·지급은 영구 Level 0이므로 이 테이블의 쓰기 경로도 owner 전용이다
(패널 붙일 때 `ownerOnly` 가드 — `/api/admin/course*`와 같은 규칙).

## 5. 권한 — 스코프 단위가 학생에서 등록으로 내려간다

`docs/lecture-data-model.md` §3.1의 구멍(스코프가 *학생* 단위인데 학생이 겹친다)의
레슨 쪽 종착이 `lesson_enrollments.trainer_id`다. 병행수강(트레이너 2명)은 학생당
등록 2행으로 표현되고, 트레이너 필터는 `x.trainer_id === c.me.id`(학생 기준)에서
등록 기준으로 옮겨 간다. `students.trainer_id`는 병행 단계 동안 유지하고, 봇 v2
재배선이 등록 기준 조회로 전환한 뒤 폐기를 별도 판단한다.

`lesson_sessions.lesson_enrollment_id`(§19e)는 백필(8/18~22)에서 채운다 —
세션의 시점·트레이너로 등록에 귀속시키되, FIFO 경계(§1)와 일치하는지 검산한다.

## 7. 장익교 병합 (D1 · Level 0)

`students`에 장익교가 2행(§8.2 확정 중복 — PUBG닉 `GmI_IkeJang` 동일) 있고, DB
`payments`에는 원장에 없는 **07-15 · 120,000 행이 하나 더 있다**(원장은 05-07 1차 +
07-11 추가뿐). 유력 가설은 "같은 추가결제가 두 학생 행에 각각 기입"이지만, 실측 없이
병합하면 안 된다 — 07-15가 실결제면 삭제가 매출 소실이다.

검증 쿼리 2건(채팅으로 전달)의 회신을 받아 병합 SQL을 확정한다. 병합이 백필(D3)보다
먼저여야 하는 이유: 세션·결제 귀속이 두 학생 행에 갈라져 있으면 등록 귀속도 갈라진다.

## 8. 검산

- 등록별 `Σ payments(귀속).amount` — 원장 해당 트랜치 합과 일치 (환불 음수 포함)
- 등록별 `잔여 = games_total − Σ sessions(귀속).games` — 레슨로그 잔여와 일치
- `payments`에 `course_id`·`lesson_enrollment_id` 동시 보유 0건 (CHECK가 막지만 실측 재확인)
- CHECK 제약 존재 확인은 컬럼 프로브로 불가 — `pg_constraint` 조회로만:

```sql
select conname, pg_get_constraintdef(oid) from pg_constraint
 where conrelid='public.payments'::regclass and contype='c';
```
