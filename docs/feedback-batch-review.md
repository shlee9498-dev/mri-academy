# 피드백 일괄 검토 뷰 — 설계

> 관제탑 2026-08-18 지시 7. **설계만 · 구현 금지.**
> 실측은 전부 실DB 조회(2026-08-18).

---

## 1. 진단 — 병목은 "한 건씩 처리"가 아니다

지시문의 전제는 "✅ 즉시 노출 구조인데 55일 대기 = 한 건씩 처리하는 구조가 병목"이었다.
실측하면 원인이 다르다.

| 항목 | 실측 |
|---|---:|
| 미승인(`published=false` · `rejected` 아님) | **29건** |
| 그중 `review_msg IS NULL` | **29건 (100%)** |
| 공개된 적 있는 행(`published=true`) | **0건** |
| 반려된 적 있는 행(`rejected=true`) | **0건** |
| 최초 미승인 | 2026-06-23 (55일) |
| 수집 출처 채널 수 | 9개 · 트레이너 1명 |

**29건 전부 `review_msg`가 없다.** `src_msg`·`src_channel`·`src_guild`는 29/29 다 있으므로
디스코드 수집 자체는 성공했고, **검수 채널 프리뷰 게시만 실패**했다는 뜻이다
(`server.js` `fb_preview` catch — 게시 실패해도 행은 남는다).

> 즉 **누를 ✅ 자체가 없다.** 승인이 느린 게 아니라 승인 UI가 생성되지 않았다.
> `published`·`rejected`가 둘 다 0건인 것이 이를 뒷받침한다 — 이 파이프라인은 **한 번도
> 승인을 통과한 적이 없다.**

이 진단이 설계를 바꾼다. 일괄 뷰는 **디스코드 메시지에 의존하면 안 된다.** `review_msg`가
없는 29건은 리액션 경로로는 영원히 처리할 수 없다. DB를 직접 읽고 직접 쓰는 화면이어야 한다.

### 1.1 부수 발견 — 공지문이 피드백으로 수집된다

미승인 29건 중 **최소 5건**이 같은 공지문이다(6/23 · 7/14 · 7/18 · 7/24 · 7/28):

```
📢 피드백 채널 이용 안내
이 채널은 단순한 메모장이 아닙니다. …
```

수집 조건이 "15자 이상 + 채널명 파싱 성공"뿐이라 채널에 다시 붙는 공지가 그대로 들어온다.
**일괄 반려가 가장 먼저 필요한 대상이 이것**이고, 동시에 수집 단계 필터가 따로 필요하다는
신호다(§5).

## 2. 설계 원칙

1. **DB가 정본.** 화면은 `feedback` 테이블을 직접 읽는다. 디스코드 메시지 존재 여부와 무관하게
   모든 미승인 행이 보여야 한다 — 그러지 않으면 지금의 29건이 그대로 안 보인다.
2. **공개는 되돌릴 수 있어야 한다.** ✅ = 즉시 사이트 노출인데(`/api/feedback-public`),
   일괄 승인은 실수의 규모도 같이 키운다. 되돌리기(공개 → 미공개)를 같은 화면에 둔다.
3. **기존 리액션 경로를 죽이지 않는다.** 두 경로가 같은 컬럼(`published`·`rejected`)을 쓰므로
   공존한다. 리액션으로 처리된 건은 목록에서 자동으로 빠진다.
4. **정산과 무관하다.** 피드백은 금액을 만들지 않는다 — `PANEL_WRITE` 게이트를 그대로 적용하면
   컷오버 전까지 못 쓴다. `/api/admin/schedule*`과 같은 예외로 둘지는 **오너 판정**(§6).

## 3. 화면 — staff-panel 「피드백 검수」 탭

```
┌ 피드백 검수 (미승인 29)                    [전체 선택] [선택 공개] [선택 반려] │
├──────────────────────────────────────────────────────────────────────────────┤
│ ☑ #12  현태 · A그룹 · 레슨생 B · 2026-08-01          [공개][반려]            │
│      📅 레슨 날짜: 2026. 08. 01 / 🎯 오늘 배운 내용: …            (본문 4줄) │
│      ⚠️ 검수 메시지 없음 — 디코 ✅ 경로로는 처리 불가                        │
├──────────────────────────────────────────────────────────────────────────────┤
│ ☑ #7   현태 · A그룹 · 레슨생 A · 2026-07-28   🔁 반복 공지 추정              │
│      📢 피드백 채널 이용 안내 …                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

- **카드 = 1행.** 체크박스 + 메타(트레이너·그룹·별칭·레슨일) + 본문 4줄 접힘(클릭 시 펼침).
- **🔁 반복 공지 추정 배지** — 같은 본문 앞 120자가 3회 이상 반복되면 붙인다. 이 배지가 붙은
  카드는 **기본 체크 해제**로 두고, 별도 버튼 `[공지 일괄 반려]`로 한 번에 처리한다.
  자동 반려는 하지 않는다 — 판정을 코드가 대신하면 진짜 피드백이 조용히 사라진다.
- **⚠️ 검수 메시지 없음** — `review_msg IS NULL`인 행에 표시. 지금은 29/29가 여기 해당하고,
  프리뷰 게시가 복구되면 이 배지가 사라지는 것으로 복구를 확인할 수 있다.
- 정렬 기본값 = 오래된 순(대기일 큰 것부터). 55일 건이 맨 위로 온다.
- 상단에 **대기 일수 분포**(최장 / 30일↑ / 7일↑ 건수)를 한 줄로 — 다시 55일까지 가는 걸 막는다.

## 4. API (신설 2개 · `admin-panel.js`)

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/api/admin/feedback?status=pending\|published\|rejected&limit=200` | 목록. `raw`는 내려주지 않는다(원문 PII) — `body`(정제본)만. |
| POST | `/api/admin/feedback/bulk` | `{ ids:[...], action:"publish"\|"reject"\|"unpublish" }` |

**bulk 규칙**

- `ids`는 **최대 50개**로 제한한다. 한 번에 전량을 뒤집는 실수를 물리적으로 막는다.
- 서버가 각 id의 현재 상태를 읽고 **변화가 있는 행만** patch한다(멱등 · 중복 클릭 방어).
- 응답은 `{ changed:[ids], skipped:[{id, reason}] }` — 몇 건이 실제로 바뀌었는지 화면에 뜬다.
- `admin_audit`에 1건으로 남긴다(`action="feedback_bulk"`, `detail={action, count, ids}`).
  개별 행마다 남기면 감사 로그가 피드백으로 덮인다.
- 권한: **owner 전용.** 트레이너가 자기 피드백을 스스로 공개하는 경로를 만들지 않는다.

## 5. 함께 고쳐야 하는 것 (이 설계 밖 · 별건)

1. **프리뷰 게시 실패가 조용하다.** `fb_preview` catch가 `console.error`만 하고 끝난다.
   행은 남고 검수 메시지는 없는 상태가 29건 쌓이도록 아무도 몰랐다.
   → 실패 시 `review_msg`에 sentinel(예: `'FAILED'`)을 남기거나 오너 DM 1건.
   `runFeedbackPending`이 이미 매일 도는데 **개수만 세고 `review_msg`는 안 본다** — 여기에
   "검수 메시지 없는 건 N" 한 줄을 더하면 같은 사고가 다시는 55일을 못 간다.
2. **수집 단계 공지 필터.** 15자 길이 조건만으로는 공지가 걸러지지 않는다.
   본문에 레슨 날짜 패턴(`📅` 또는 `레슨 날짜`)이 없으면 수집하지 않는 것이 가장 단순하다
   (현재 29건 중 실제 피드백은 전부 이 패턴을 갖고 있다).

## 6. 오너 판정 필요

| ID | 항목 | 권고 |
|---|---|---|
| F-1 | `PANEL_WRITE` 예외 여부 | **예외 부여**(schedule과 동일 논거 — 정산 무관). 예외를 안 주면 컷오버까지 이 화면을 못 쓴다 |
| F-2 | 반복 공지 5건 처리 | 일괄 반려 |
| F-3 | 나머지 24건 공개 범위 | 전량 공개 vs 선별 — 공개는 즉시 사이트 노출이라 첫 회는 선별 권고 |
| F-4 | 수집 필터 강화(§5-2) | 적용 |

## 7. 구현 순서 (승인 시)

1. GET API + 목록 화면(읽기 전용) — 29건이 화면에 보이는 것만으로 진단이 끝난다
2. bulk API + 버튼 (F-1 판정 후)
3. §5 프리뷰 실패 감지 + 수집 필터 (별도 PR — 봇 영역)
