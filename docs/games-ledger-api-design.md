# 판수 내역 API + 30분 예약 + 차감 종류 — 설계 (2026-09-27 · 오너 지시)

**설계만.** DDL·코드 착수는 오너 확정 뒤. 「최종」 블록은 확정 후 별도 발행.

## ⓞ 왜 급한가

오픈 첫날 **두 명이 같은 문의**를 했다 — 「내 판수가 왜 이 숫자냐」. 한 명은 실제로
**중복 적립**을 찾아냈다(명부 #14 · 2026-09-27 정정 완료). 잔여 숫자 하나만 보여주면
운영자가 매번 SQL 로 대조해야 하고, 수강생은 틀린 줄도 모른다. **내역이 보이면 수강생이
스스로 검산한다** — 첫날에 그게 실제로 작동했다.

## 1. `GET /api/student-portal/games-ledger`

잔여 판수의 **모든 증감을 날짜순 한 줄씩** 내린다. 누계를 서버가 계산해 싣는다.

```jsonc
{
  "remain": 12,                       // 현재 잔여 = 마지막 줄의 balance
  "rows": [
    { "at": "2026-05-04", "kind": "enroll",  "games": +10, "balance": 10,
      "trainer": "준구", "note": "등록", "voided": false },
    { "at": "2026-05-14", "kind": "enroll",  "games": +10, "balance": 20,
      "trainer": "무리", "note": "등록", "voided": false },
    { "at": "2026-05-14", "kind": "enroll",  "games":   0, "balance": 20,
      "trainer": "무리", "note": "중복 적립분 — 무효 처리(2026-09-27)", "voided": true },
    { "at": "2026-07-19", "kind": "lesson",  "games":  -8, "balance": 12,
      "trainer": "현태", "note": "수업" },
    { "at": "2026-09-28", "kind": "hold",    "games":  -5, "balance":  7,
      "trainer": "현태", "note": "예약 선차감 · 09-28 11:00 개인 60분" }
  ]
}
```

### 1.1 줄의 출처 — 새 표가 필요 없다 (실측)

| kind | 출처 | 부호 |
|---|---|---|
| `enroll` | `lesson_enrollments` (`started_on`·`games_total`·`trainer_id`) | + |
| `lesson` | `lesson_sessions` (`played_at`·`games`·`trainer_id`) | − |
| `adjust` | `lesson_sessions` 중 **보정 행** — `/판수정정` 이 원본을 고치지 않고 append 한다 | ± |
| `hold` | `slot_bookings` (`games_held`·`booked_at`, 상태 `booked`·`pending_review`·`no_show`) | − |
| `carry` | `students.carry_games` ≠ 0 이면 맨 앞 한 줄(7/20 이월 스냅) | + |

**취소·무효 줄은 지운 것이 아니라 `games: 0` + `voided: true` 로 남긴다.** 이희훈 건처럼
「왜 30판이 20판이 됐나」를 수강생이 직접 볼 수 있어야 한다. 이게 이 API 의 존재 이유다.

⚠️ `adjust` 와 `lesson` 을 **`memo` 로 가르지 않는다** — 문자열 판정은 언젠가 깨진다.
현행에는 구분 컬럼이 없으므로 §3 의 `entry_kind` 로 해결한다. 그때까지는 **둘 다 `lesson`**
으로 내리고 `note` 에 memo 를 싣는다(틀린 분류를 내보내느니 합쳐서 보여주는 쪽이 낫다).

### 1.2 잔여와 반드시 같아야 한다

마지막 `balance` 는 `portal_remaining_games()` 와 **한 자리도 달라선 안 된다.**
그 함수가 쓰는 네 항(`carry_games` + Σ등록 − Σ사용 − Σ선차감)과 **같은 상태 목록**을
쓴다. 지금 그 목록이 **세 곳에 복제**돼 있으므로(`booking-policy-design.md` §2.5) 이
API 가 네 번째 사본이 되면 안 된다 — **`portal_remaining_games` 를 호출해 검산하고,
어긋나면 응답에 `mismatch: true` 를 실어 조용히 틀리지 않게 한다.**

### 1.3 트레이너 화면

`GET /api/trainer-portal/students/:id/games-ledger` — 같은 모양. 범위는
`scopedStudents()`(담당 ∪ 최근 90일). 트레이너가 수강생 문의를 그 자리에서 답할 수 있어야
운영자에게 안 올라온다.

## 2. 🔴 「트레이너별 잔여」 — 지금 데이터로는 규칙 없이 못 낸다

수강생 문의: 「잔여 12판이 현태 2 · 준구 10 인데 앱에서 구분이 안 된다」.

### 2.1 실측

| | 값 |
|---|---|
| `lesson_sessions` 전체 | **238** |
| 그중 `lesson_enrollment_id` 로 **등록에 귀속된 것** | **174 (73%)** |
| 미귀속 | **64 (27%)** |
| 등록 트레이너 ≠ 수업 트레이너인 등록 | **23건 · 수강생 9명** |
| 등록 트레이너가 2명 이상인 수강생 | **8명** |
| **명부 #14 의 수업 1건** | **미귀속** (`lesson_enrollment_id` null) |

### 2.2 두 축이 서로 다르다 — 이게 핵심이다

- `lesson_enrollments.trainer_id` = **급여 귀속** 축. 결제를 처리한 사람이다.
- `lesson_sessions.trainer_id` = **실제 수업** 축. 학생이 「누구 판수」로 인식하는 쪽이다.

명부 #14 에서 둘이 갈린다. 등록 #28 의 트레이너는 **무리**이고(memo: 「오너 판정 8/14 …
**급여 귀속 무리**」), 수업 8판은 **현태**가 했다. 그래서:

| 축 | 결과 | 학생 기대 |
|---|---|---|
| 등록 트레이너 기준 | 무리 2 · 준구 10 | ✗ |
| 수업 트레이너 기준(FIFO) | **현태 2 · 준구 10** | ✅ |

**학생은 수업 축으로 센다.** 급여 축으로 화면을 만들면 문의가 더 늘어난다.

### 2.3 오너 판정 필요

1. **어느 축을 화면의 정본으로 하나** — 수업 축을 권한다(학생 기대와 맞고, 급여 축은 정산
   화면이 따로 쓴다).
2. **등록 ↔ 사용을 어떻게 잇나** — `lesson_enrollment_id` 가 73% 채워져 있다.
   나머지 27% 를 ⓐ FIFO 로 소급 채울지 ⓑ 비워 두고 「미귀속」으로 표시할지.
   ⓐ 는 데이터 변경(Level 0)이고, 소급 규칙이 틀리면 트레이너별 숫자가 통째로 틀린다.
3. **등록 트레이너와 다른 트레이너가 수업하면 어느 쪽에서 빼나** — 규칙이 **지금 없다**.
   실무는 「학생이 고른 트레이너에게서 뺀다」에 가깝다(#14 가 그 모양).

⚠️ **판정 전에는 트레이너별 잔여를 화면에 내리지 않는 쪽을 권한다.** 틀린 숫자를 보여주면
지금의 「구분이 안 된다」보다 나쁘다. §1 의 내역만으로도 수강생은 줄마다 트레이너를 보고
스스로 셀 수 있다.

## 3. 차감 종류 구분 → **정본 이동**

> **이 절의 설계는 `docs/booking-policy-design.md` §2.7 로 옮겼다**(오너 지시 2026-09-27:
> 「벌점 설계는 이 세션 하나로 · 판수 로직을 두 벌로 만들지 않는다」). 여기서 다시 적지 않는다 —
> 두 벌이 되면 어긋난다.

옮긴 내용: `lesson_sessions.entry_kind`(`lesson`·`no_show`·`late_cancel`·`adjust`·`waived`) ·
노쇼 확정 절차(+10분 표시 → 24시간 → 확정) · `no_show_marked_at`/`no_show_settled_at` ·
선차감(hold)과 차감(확정)의 구분 · 트레이너 3시간 이내 취소.

**이 문서가 계속 책임지는 것**은 그 종류를 *어떻게 내려주는가*다 — 내역 API 가 `entry_kind` 를
줄의 종류로 그대로 내리고(「늦은 취소 −3 · 9/28 · 현태」), 확정 전 노쇼는 `hold` 로, 확정 뒤에는
`no_show` 로 내린다(§1).

## 4. 30분(3판) 개인 예약

가격 정본 차감표: **30분 3판 · 1시간 5판 · 1시간 30분 8판 · 2시간 10판.**
서버는 지금 **60·90·120 만** 받는다 — 30분이 빠져 있다.

### 4.1 바뀌는 것 — 두 줄

```sql
-- book_slot 안
v_games := case p_duration_min when 30 then 3 when 60 then 5
                               when 90 then 8 when 120 then 10 else null end;
```
```js
// booking-api.cjs
const DURATION_MIN = [30, 60, 90, 120];
```

`v_need := p_duration_min / 30` → **30/30 = 1칸**. 연속 칸 묶기 로직이 그대로 성립하고,
꼬리 행 insert 는 `where x <> v_slot.id` 라 **0행이 들어간다**(머리 하나뿐). 구조 변경 없음.

3시간 마감 · 정원 · 상담 예외 · 잔여 검사 전부 **무변경**.
`/availability` 의 `personalDurations` 가 배열을 그대로 내리므로 앱은 자동 반영된다.

### 4.2 ⚠️ 대가 — 격자가 조각난다

30분 예약이 한가운데 들어가면 **90·120 을 놓을 자리가 줄어든다.** 실측으로 지금 현태의
연속 블록 8개 중 7개가 10~14칸이라 당장은 여유가 있지만, 예약이 차면 30분이 긴 수업을
밀어낸다. 운영에서 문제가 되면 ⓐ 30분은 블록 **끝**에서만 허용 ⓑ 트레이너가 슬롯을 열 때
「30분 허용」을 고른다 — 둘 다 이번 범위 밖이고, 필요해지면 별건으로 본다.

### 4.3 DDL 「최종」 3단 — 확정 후 발행

`book_slot` `create or replace` 한 줄 변경뿐이다. **§32·둘 다 슬롯·대행 예약과 같은
회차로 묶어야 한다** — 넷 다 `book_slot` 을 덮어쓰므로 따로 실행하면 나중 것이 앞의 것을
지운다. 지금 대기 중인 `book_slot` 변경은 **넷**이다:

| 회차 항목 | 내용 |
|---|---|
| §32 | 취소 3시간 · 예약 마감 3시간 (**실행 완료** · 지문만 어긋남) |
| 둘 다 슬롯 | `offer_group` 분기 + 그룹 선점 검사 |
| 대행 예약 | `p_skip_lead` 인자(A안 채택 시) |
| **30분** | `when 30 then 3` |

### 4.4 반장 계약 한 줄

> `GET /api/student-portal/availability` 의 `personalDurations` 에 **30** 이 추가된다
> (`[30, 60, 90, 120]`). 30분은 **3판 선차감 · 칸 1개**이고 3시간 마감·잔여 검사는 동일하다.
> 앱은 이 배열을 그대로 그리면 되고 하드코딩된 길이 목록이 있으면 지운다.
> 오류 코드 변화 없음.

⚠️ 21:15 KST 에는 **참여형 14칸**(월 19:00~화 01:30)이 있었는데 지금은 0 이다 —
트레이너가 지웠다. 수강생이 「1:1 만 보인다」고 한 것은 **화면 문제가 아니라 실제로 그것만
열려 있어서**다.

**「1시간만 보인다」는 앱 쪽이다.** 서버는 `personalDurations: [60, 90, 120]` 을 그대로
내리고, 현태의 연속 블록 8개 중 **7개가 10~14칸**이라 60·90·120 이 전부 들어간다
(12:00 블록만 2칸이라 60 만 가능). 즉 **데이터는 세 길이를 받칠 수 있는데 화면에 하나만
뜨고 있다** → 반장 확인 항목.
