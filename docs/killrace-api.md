## §0 지금 돌아가는 것 (2026-10-06 4회 기준 · 요약)

| 무엇 | 어디 | 메모 |
|---|---|---|
| 대회 한 줄 | `event_defs` (이름 · `window_start` · `window_end`) | 판 인정 = 매치 시작 시각이 `[시작, 끝)` 안(노래방룰). 줄은 지금 DB 에 직접 넣는다 |
| 팀 | `event_teams` (2~4명 · 슬롯 · 교체 선수 `sub`) | `/킬내기팀등록`(오너) · 경매 마감 등록. 슬롯 1번 = 최상위 티어 |
| 판 | `event_matches` (팀 × 매치 한 줄) | 판 점수 · `deaths.members`(선수별 킬 · 딜 · deathType · 계정 번호) · `flags` |
| 대회 설정 | `ops_state` `killrace:event:<id>` | `boostMode`(`time`/`seq` · §1.13) · `boostSeqs`([5, 7]) · `boostAt` · `boostMul`(1.5) · `lateRevive`(`penalty`/`flag`/`off` · §1.14) · `revivePhase`(4) · `bonus{팀명: 점}` · `auto` · `voidDeaths` · `voidGames` · `liveTokens` |
| 자동 집계 | `killrace-live.cjs` `tick()` 1분마다 | 시작 ~ 끝 + 45분 · PUBG 조회 · 실패 3번 연속이면 멈춤 |
| 점수판 | `GET /api/killrace/board` · `/players` · `/events` | `?event=<번호>` = 지난 회차(읽기만) |

**점수식은 이 문서 범위 밖이다(바꾸지 않는다)** — 버닝 판을 고르는 방식(§1.13)과 늦은 부활 −10(§1.14)만 오너 OK(10/7)로 바꿨다. 판 점수 = 킬 + floor(팀 딜 합 / 100) + 치킨 8 − 사망 슬롯 감점(1번 4 · 2번 3 · 3번 2 · 4번 1),
이탈 −10 고정(**5회부터 4페이즈 뒤 부활 비행기 탑승도 −10** · §1.14), 버닝 판 × 1.5(2 · 3 · 4회 = 버닝 시각 뒤 처음 시작한 판 하나 · **5회부터 = 팀마다 5 · 7번째 판** · §1.13), 총점 = Σ판 + `bonus[팀명]`.
4회부터 쓰는 시작 보너스(남은 포인트 5P당 +1 · 마이너스는 5P당 −2 · 7티어 1명당 +5 · 8티어 1명당 +10)는 **계산 결과를 `bonus` 값으로 넣는 방식 그대로**다.

**「지금 대회」 = `event_defs` 에서 번호가 가장 큰 줄**(`killrace.currentEvent()`). 팀 등록 · 교체 · 점수판 기본 화면 · 진행자 동작 · 팀 주소 · 스샷 · 경매가 전부 이 줄을 본다.

## §1 킬내기 무인 운영 — 1단계 (2026-10-06 · 지휘 주문 · 오너 OK)

오너 원문(2026-10-06 23:3x KST): 「킬내기 어플을 하나 만들자 … 킬내기 시스템 봇으로 돌릴거야 내가 없어도 돌아가는 구도로」 ·
「다음에 팀장정할 땐 저 상위티어전투력처럼 판단되는 거로 해서 1~5 팀장정해줘」 · 「ㅇㅋ 좋다 지금부터 만들기 시작해보자」.

목표: 10/6 4회에서 오너 손이 들어간 곳을 기계가 한다 — 휘슬(시각) · 명단(신청 · 경매 · 등록) · 점수판(창 이동 · 보너스 입력 · 결과 게시).
1단계는 **지금 서버 위에서** 한다(새 앱은 2단계). 이 절의 번호 n = 설계 v0 4장 1단계 n번.

### §1.0 공통 규칙

- **권한 등급** — 오너(디스코드 `MRI_OWNER_ID` · 오너 JWT) · 진행자(`x-admin-key` = `gdcupAdmin`) · 팀장(경매 개인 링크 토큰) ·
  팀 주소(잠정 킬 토큰) · 공개(점수판 · 개인 기록). 서버 자동(1분 tick)은 권한 판정 없이 돈다.
- **추정값으로 채우지 않는다** — 읽지 못한 값 · 조회 실패는 빈칸과 이유로 남긴다(스샷 「못 읽었어요」와 같은 원칙).
- **실패는 그 대회 · 그 단계에만 머문다** — 한 대회 · 한 팀 · 한 선수의 실패가 다른 대회 집계나 다른 팀 등록을 막지 않는다.
- **개인정보** — 공개 응답에는 닉 · 슬롯 · 숫자만. PUBG 계정 번호(`account.…`)는 진행자 · 오너 응답에만. 계좌 · 디스코드 id 는 지금 경계 그대로
  (계좌 = 오너 JWT 전용 · `killrace-apply.cjs` 머리말).
- **DB 구조 변경은 더하기만**(새 표 · 새 칸 · 새 인덱스). 기존 칸 · 표 · 점수식은 그대로 둔다. DDL 은 대회 시간 밖에 스냅샷 → 실행 → 검증 → `notify pgrst` 순서.
- **대회 시간(창 시작 ~ 끝 + 45분)에는 머지 · 배포 · DDL 을 하지 않는다.**

### §1.1 참가 신청 — 디스코드 버튼 또는 웹 한 번 · 그 자리에서 계정 번호로 저장

지금: `killrace-apply.cjs` 웹 솔로 신청(2회용 · 회차 `r2` · 마감 시각 · 정원 20 이 코드에 박혀 있음) · 닉만 받고 계정 번호는 경매 뒤 팀 등록 때 처음 조회한다.

- **입력** — 회차(지금 대회 번호) · 스팀 닉 · (웹) 디스코드 닉 · 상금 계좌. 디스코드 버튼은 모집 글의 「신청」 버튼 → 입력 창(스팀 닉 한 칸).
- **처리** — 받은 자리에서 PUBG 닉 조회 → **계정 번호(accountId)와 정확한 닉으로 저장**(대소문자만 다르면 바로잡는다 · `pickPlayer` 규칙).
  같은 계정 번호는 한 회차에 한 번. 정원(설계 5장 규격 · 기본 20)까지 「참가」, 그 뒤 「대기」, 취소가 나오면 대기 맨 앞이 올라온다(지금 규칙 그대로).
- **출력** — 신청자에게 한 줄(「신청 완료! ○번째예요」 · 대기면 「대기 ○번」) · 진행자 화면 명단(닉 · 계정 확인 여부 · 상태).
- **저장** — `ops_state` `killrace:apply:<event id>`(지금 `r2` 형식을 회차 번호로) · 계좌는 지금처럼 따로 한 줄(오너 전용).
- **권한** — 신청 = 누구나(버튼은 GmI 길드 회원) · 명단 = 진행자(계좌 없음) · 계좌 = 오너.
- **실패 시** — 닉을 못 찾음 → 저장하지 않고 「스팀에서 못 찾았어요. 대소문자까지 다시 한 번 볼까요?」 · PUBG 조회 실패 → 저장하지 않고 다시 해 달라고 한다
  (닉만으로 받아 두지 않는다 — 닉 변경 · 대소문자 사고를 막는 게 이 절의 목적) · 마감 뒤 → 거절.

### §1.2 티어 자동 산정 — 누적 판 기록으로

- **입력** — §1.8 개인별 판 기록의 **인정 판**(`seq` 있고 이탈 아님)만. 계정 번호 기준(닉이 바뀌어도 이어진다).
- **출력** — 계정마다 `{ games, avgKills, avgDamage, topKillRate(팀 내 킬 1등 비율), deathRate, sample }` + 제안 티어(1~8).
  팀 내 킬 1등 = 그 판 같은 팀에서 킬이 가장 많은 선수(공동이면 모두 1등). **10판 미만은 `sample: "부족"`** 으로 표시하고 티어를 제안하지 않는다.
- **티어 구간** — 지표 → 1~8 티어 경계는 **오너 결정 대기**(설계 8장). 정해지기 전에는 지표만 내고 티어는 운영자가 넣는다. 첫 참가자도 운영자 입력.
- **권한** — 지표 · 티어 = 공개(닉 · 숫자) · 계정 번호 = 진행자.
- **실패 시** — 판 기록이 없는 선수 = 「표본 부족」. 계산은 DB 만 읽는다(PUBG 조회 없음 → 조회 한도와 무관).

### §1.3 팀장 자동 추천 — 지표 상위 1~N위

- **입력** — 그 회차 신청 명단(§1.1 「참가」) + §1.2 지표. 팀 수 N = 신청 인원 규격(설계 5장: 12~15명 3팀 · 16~19명 4팀 · 20~23명 5팀).
- **출력** — 전투력 점수 순 1~N위 + 다음 순위 2명(예비). 전투력 = 평균 킬 · 평균 딜 · 팀 내 킬 1등 비율의 가중 합 —
  가중치는 오너 결정 대기, 그 전에는 10/6 지휘 실측 「3티어 이상 전투력」(평균 킬 · 평균 딜 · 팀 내 1등 횟수)을 같은 순서로 쓴다.
  N위와 N+1위 점수 차가 기준(기본 5%) 안이면 「운영자 확인」 표시.
- **권한** — 진행자(추천 보기 · 확정). 확정한 팀장은 §1.4 경매로 넘어간다.
- **실패 시** — 표본 부족 신청자는 후보에서 빼고 따로 보여 준다. 후보가 N 보다 적으면 모자란 자리는 운영자가 지명.

### §1.4 경매 화면 — 타이머 · 입찰 · 자동 낙찰 · 남은 포인트 · 보너스 자동 계산

지금: `killrace-auction.cjs` 가 2회 규칙(티어 3단 · 남은 포인트 10당 +1)으로 있다. 4회 규칙(티어 1~8 · 5P당 1점 · 마이너스 2배 · 7/8티어 가산)은 아직 코드에 없어 4회는 손으로 했다.

- **입력** — 회차 설정 `{ budget, startPrice{1..8: 40 · 30 · 25 · 20 · 15 · 10 · 5 · 5}, bidSec, minStep, bonusPer: 5, negativeMul: 2, tierBonus{7: 5, 8: 10} }` ·
  팀장(§1.3) · 선수(§1.1 · 티어 §1.2).
- **출력** — 낙찰 · 유찰 · 팀별 남은 포인트 · **시작 보너스 = 남은 포인트 보너스 + 티어 가산**.
  남은 포인트 보너스: 0 이상이면 floor(P / 5), 마이너스면 −2 × floor(|P| / 5)(5P 단위로만 · 나머지는 버림) — **5의 배수가 아닐 때 버림은 오너 확인 대기**(10/6 4회 값은 모두 5의 배수였다).
- **권한** — 진행자(시작 · 매물 · 마감) · 팀장(입찰 · 개인 링크) · 공개(보기).
- **실패 시** — 상태는 `ops_state` `killrace:auction:<id>` 한 줄이라 서버가 다시 떠도 이어진다. 시각은 서버 기준(지금 그대로). 같은 순간 입찰은 먼저 도착한 것만.

### §1.5 자동 등록 — 경매가 끝나면 팀 · 슬롯 · 시작 보너스를 그대로 저장

- **입력** — §1.4 마감 결과.
- **출력** — `event_teams`(슬롯 = **티어 높은 순 1 → 4번** · 같은 티어면 낙찰가 높은 순 · 계정 번호는 §1.1 에서 받은 값) ·
  `killrace:event:<id>.bonus`(§1.4 시작 보너스) · `killrace:roster:<id>`(티어 · 낙찰가 · 팀장).
- **권한** — 진행자 「등록」 한 번(마감과 같은 화면). 등록 결과는 진행자 화면 · 오너 DM.
- **실패 시** — 한 팀이 실패해도 나머지는 등록한다(지금 그대로). 실패한 팀은 이유와 함께 남기고 보너스는 등록된 팀만 넣는다. 같은 팀명 재등록은 대회 중 금지(앞 판이 빠진다 · 교체는 `/킬내기교체`).

### §1.6 여러 대회 동시 진행 — 창이 열린 대회를 모두 집계 (조각 B · 구현)

배경: 서버가 「가장 큰 번호 = 지금 대회」 하나만 집계했다. 10/6 3회 막판 집계(21:50 + 45분 = 22:35)가 끝나기 전에 4회 줄(22:20 시작)을 만들면
그 순간 3회 집계가 멈추기 때문에 줄을 22:29 에 만들었고, 오너 팀 등록이 그만큼 밀렸다.

- **열린 대회** = 지금 시각 t 가 `[window_start, window_end + 45분]` 안인 대회. 45분 = 끝 직전에 시작한 판이 끝나고 전적이 올라올 때까지(종전 그대로).
- **자동 집계(1분)** — 열린 대회를 **모두**, 번호 큰 것부터 하나씩 차례로 집계한다. 대회마다 따로 본다: 자동 꺼짐(`auto`) · 멈춤(연속 3번 실패) · 팀 없음.
  집계 상태(`ops_state` `killrace:live:<id>` 의 `run` · 잠정 킬 · 순위 변동)도 대회마다 따로 저장한다(키는 종전과 같다).
  한 번에 보는 열린 대회는 **번호 큰 순 5개까지**(넘치면 로그 한 줄).
- **「지금 대회」는 그대로 가장 큰 번호** — 팀 등록 · 교체 · 점수판 기본 화면 · 개인 기록 기본 · 진행자 동작 · 팀 주소 · 스샷 · 경매 · 신청.
  → 운영 순서가 이렇게 바뀐다: **다음 회차 줄은 앞 회차 막판 집계 중에 만들어도 된다.** 줄을 만드는 순간 점수판 기본 화면과 팀 등록은 새 회차로 넘어가고,
  앞 회차는 끝 + 45분까지 계속 집계된다. 앞 회차 화면은 회차 고르기(`?event=<번호>` · 30초 캐시)로 본다.
  - **줄을 만드는 순간 넘어가는 화면**(§1.7 `eventCreate` · DB 에서 직접 만들어도 같다) — 점수판 기본 화면 · 개인 기록 기본 화면 ·
    **방송 오버레이**(`killnaegi-overlay.html` · `killnaegi-overlay-v2.html` — 회차를 고르는 칸이 없다). 앞 회차는 `?event=<번호>` 로만 보인다.
    앞 회차 막판 순위를 방송에 계속 띄워야 하면 다음 줄을 앞 회차 끝 + 45분 뒤에 만든다.
  - **스샷 봇도 새 회차로 넘어간다** — `killrace-shot.cjs` 는 사진을 「지금 대회」 팀에 맞춘다. 새 줄을 만든 뒤 올라온 앞 회차 막판 결과 사진은
    같은 선수가 든 새 회차 팀에 「잠정」으로 붙을 수 있다. 잠정 칸만이고 총점 · 순위는 안 바뀐다(새 회차 판 전적이 오거나 표시 시간이 지나면 사라진다).
    앞 회차 확정 점수는 전적으로만 들어간다.
- **입력 · 출력**
  - 서버 `tick()`(1분) — 반환: 열린 대회가 하나면 종전 값 그대로(`ran` · `auto_off` · `paused` · `no_teams` · `failed` · `busy`),
    둘 이상이면 `<번호>:<값>` 을 빈칸으로 이은 글(`4:ran 3:ran`). 열린 대회가 없으면 지금 대회 기준 `before_start` · `after_end`, 대회가 없으면 `no_event`(종전 그대로).
    차례가 아직 도는 중이거나 준비가 안 됐으면(`PUBG_API_KEY` · DB) `skip`.
  - `POST /api/killrace/board/admin` `{ action: "run", event?: <번호> }` — 진행자 「지금 집계」. `event` 가 없으면 지금 대회(종전 그대로),
    있으면 그 회차(창 밖이어도 한 번 돈다 = 종전 수동 집계와 같다). 숫자가 아니면 400 `bad_event` · 없는 번호면 404 `no_event`.
  - 로그 — `[killrace-live] run_ok source=<auto|manual> event=<번호> ms=<…>`.
- **권한** — 자동 = 서버. 「지금 집계」 = 진행자(`x-admin-key`).
- **실패 시** — 한 대회의 실패는 그 대회 `run` 에만 남는다(실패 횟수 · 멈춤이 대회마다). 다른 대회는 그 차례에 그대로 돈다.
  PUBG `/players` 분당 10회는 **대회를 합쳐서** 지킨다(조회 간격 6.5초를 모든 대회가 같이 쓴다 — `createKillrace` 하나). 한 차례가 1분을 넘기면
  다음 차례는 `skip`(겹쳐 돌지 않는다). 계산: 열린 대회 2개 × 선수 20명 = `/players` 4번 ≈ 26초.
- **이번에 안 한 것** — 진행자 동작(이탈 · 핵 사망 무효 · 판 무효 · 자동 켜고 끄기 · 팀 주소)은 지금 대회에만 걸린다(§1.7 은 시각 · 보너스만 `event` 를 받는다 · 나머지는 다음 조각).
  점수판 기본 화면 = 가장 큰 번호(여러 방을 동시에 여는 3단계에서 방마다 주소로 나눈다).

### §1.7 진행자 화면 — 시작 · 끝 · 버닝 시각과 보너스를 직접 입력 (구현 · 서버 #514 · 화면 gmi-clancup #95)

전에는 회차 줄 만들기 · 창 옮기기 · 시작 보너스를 DB 에서 직접 고쳤다(10/6 4회: 줄 생성 · 창 25분 밀기 · 보너스 5팀 모두 세션이 SQL 로).
이제 진행자 화면(`killnaegi-board.html?host=1` 「대회 설정」 칸)에서 한다.

- **입력** — `POST /api/killrace/board/admin`. 세 동작 모두 `by`(바꾸는 사람 1~20자)가 있어야 한다 — 운영 키가 한 벌이라 이름으로 남긴다.
  - `{ action: "eventCreate", by, name, start, end, boostAt?, confirm? }` — 새 회차 줄(`event_defs`) + 버닝 시각. 이름 1~40자.
  - `{ action: "eventTimes", by, event?, start?, end?, boostAt?, confirm? }` — 그 회차(없으면 지금 대회)의 시작 · 끝 · 버닝. 안 보낸 칸은 그대로 · `boostAt: null` = 버닝 없음.
  - `{ action: "bonus", by, event?, team, points }` — 팀 하나의 시작 보너스(정수 −100 ~ 100 · `null` = 지움). 등록 전 팀 이름도 받는다(등록되는 순간 붙는다 · 10/6 4회 실측).
  - 시각은 ISO 문자열 또는 ms. 이탈 · 핵 사망 무효 · 판 무효 · 자동 켜고 끄기 · 팀 주소에는 이번에 `event?` 를 넣지 않았다(지금 대회만).
    막판 집계 중인 앞 회차는 「지금 집계」(`run` 의 `event` · §1.6)로 센다.
- **출력**
  - `eventCreate` → `{ ok, event: { id, name, start, end, boostAt } }` · `eventTimes` → `{ ok, changed, dropped, rerun }` · `bonus` → `{ ok, changed, registered }`.
  - 바꾼 기록 — 회차마다 ops_state `killrace:hostlog:<id>` = `{ v: 1, entries: [{ at, by, action, before, after, team?, dropped? }] }`(최근 200줄).
    전 → 후 는 쓰기 전에 잡는다. 옛 `boostAt` 동작도 기록에 남긴다. DDL 없음.
  - 진행자 점수판 응답(`GET /api/killrace/board` + 운영 키)에 `hostLog`(최근 30줄) · `bonusAll`(등록 전 팀 포함)을 더한다. 손님 응답에는 없다.
  - 바꾸면 점수판 캐시를 바로 비운다(화면은 5초마다 다시 받는다). 오너 DM 은 보내지 않는다 — 바꾼 기록이 그 몫이다.
- **권한** — 진행자(운영 키). 끝난 회차(끝 + 45분 뒤)는 진행자 화면에서 못 바꾼다(403 `event_closed` · 고쳐야 하면 오너 승인으로 세션이 DB 에서).
  - **오너를 가르는 방법** — 진행자 API 는 운영 키(`x-admin-key` 헤더 · Railway env `GDCUP_ADMIN_KEY`) 하나로만 인증하고 오너와 진행자를 가르지 않는다.
    그래서 「지난 회차 시각 · 보너스는 오너만」을 API 로 열지 않았다 — 끝난 회차는 어느 키로든 403 이다. 오너가 바꾸려면 오너가 세션에 말하고
    세션이 DB 에서 고친 뒤 보고한다(오너 로그인으로 여는 길은 2단계 앱 · 오너 JWT 가 있는 화면에서).
- **실패 · 되묻기**
  - 400 `need_by` · `bad_name` · `bad_time`(읽을 수 없는 시각) · `bad_window`(끝 ≤ 시작 · 6시간 초과) · `bad_boost`(버닝이 창 밖) · `bad_team` · `bad_points` · `bad_event` · 404 `no_event`.
  - 409 `event_open` — 지금 회차가 아직 집계 중(끝 + 45분 전)인데 새 줄을 만들려 할 때. 새 줄이 생기는 순간 점수판 기본 화면 · 팀 등록이 새 회차로 넘어가서다.
    `current{ id, name, end }` 를 보여 주고 `confirm: true` 로 다시 보내야 만든다.
  - 409 `would_drop` — 시작을 늦추거나 끝을 당겨 이미 인정된 판이 창 밖으로 빠질 때. `count` · `games[{ team, seq, startedAt, score }]`(20개까지)를 보여 주고
    `confirm: true` 로 다시 보내야 바뀐다. 바뀌면 바로 한 번 집계해 뺀다(`rerun` · 집계가 도는 중이면 다음 차례).
  - **창 밖이 된 저장 판** — 집계는 저장된 판을 다시 쓸 때 창 안에서 시작했는지도 본다. 창 밖이 된 판은 순번을 비우고 진행자 알림
    「대회 시각이 바뀌어 창 밖이 된 저장 판 1개(n판)는 빼고 순번을 비웠어요」를 남긴다. 2 · 3 · 4회 실측 창 밖 인정 판 0개 — 지난 결과는 안 바뀐다.

### §1.8 개인별 판 기록 저장 — `event_match_players` (조각 A · DDL §66 · 10/7 실행)

배경: 「팀 내 킬 1등 · 평균 킬 · 평균 딜」(§1.2 · §1.3 재료)을 지금은 `event_matches.deaths.members`(jsonb)를 풀어서 따로 셌다(10/6 2 · 3회 74판 실측도 그렇게 했다).
판마다 선수 한 줄씩 표로 둔다. **기존 칸 · 표는 그대로**다 — `event_matches.deaths` 는 계속 쓰고 점수 계산 · 점수판은 그것을 읽는다.

- **표** — `public.event_match_players`(판 × 선수 한 줄 · `supabase_admin_panel.sql` §66 · 더하기만)

  | 칸 | 뜻 |
  |---|---|
  | `event_id` · `team_name` · `match_id` | 그 판(`event_matches` 를 가리킨다 · 판 줄이 지워지면 같이 지워진다) |
  | `account_id` | PUBG 계정 번호 — 닉이 바뀌어도 같다. 기본 키 (`event_id`, `team_name`, `match_id`, `account_id`) |
  | `slot` · `sub` | 그 판에서 맡은 감점 슬롯(1~4) · 교체 선수로 뛴 판이면 `true`(물려받은 슬롯) |
  | `ign` · `reg_ign` | 그 판 인게임 닉 · 등록 닉이 다르면 등록 닉 |
  | `kills` · `damage` | 그 판 킬 · 딜(소수 그대로) |
  | `death_type` · `dead` | PUBG deathType 원문 · 사망 판정(감점 기준과 같은 값) |
  | `started_at` · `updated_at` | 판 시작 시각(`event_matches.created_at`) · 마지막으로 쓴 시각 |

  찾아보기 인덱스 (`account_id`, `started_at desc`) — 선수 한 명의 판을 최근 순으로. RLS 켬 · 정책 없음 = service_role 만.
- **인정 판인지는 이 표에 적지 않는다** — `event_matches` 와 맞대어 본다: `seq is not null and not leave_flag`. 이탈 · 판 무효 · 팀 구성 변경으로 빠진 판은
  줄이 남아도 맞대면 빠진다. 핵 사망 무효 슬롯은 `event_matches.flags.voidSlots`. (같은 사실을 두 곳에 두면 진행자 표시 뒤에 어긋난다.)
- **쓰는 때** — 자동 집계 · `/킬내기집계` 가 `event_matches` 를 저장한 바로 뒤, 선수 기록이 있는 판(인정 판 · 판 무효로 돌린 판)의 선수 줄을 한 번에 덮어쓴다(upsert).
  제외 판(인원 · 한 스쿼드 아님 · 모드 · 시간 밖)은 선수 기록이 없어 줄도 없다(지금 `deaths` 와 같다).
- **입력 · 출력** — HTTP 는 이 조각에 없다(§1.2 가 읽는다). 개인 지표를 셀 때:
  `event_match_players p join event_matches m using (event_id, team_name, match_id) where m.seq is not null and not m.leave_flag`.
- **권한** — 서버만(service_role). 응답 노출 범위는 §1.2(계정 번호는 진행자 · 오너만).
- **실패 시** — 이 표 쓰기가 실패해도 집계 · 점수는 그대로 저장되고 그 차례는 성공이다. 로그 `[killrace] players_write_failed <이유>` 한 줄.
  표가 없으면(§66 실행 전) 10분 동안 쓰기를 쉬었다가 다시 해 본다(1분마다 같은 실패 로그가 쌓이지 않게) · 기동 점검 `SCHEMA_OPTIONAL` 경고 1줄.
- **과거 판 채우기** — §66 실행 뒤 한 번, `event_matches.deaths.members` 를 펴서 넣는다(PUBG 조회 없음 · SQL 은 §66 에 있다).
  10/6 실측: 2회 38판 152줄 · 3회 49판 196줄 · 4회 진행 중. 모든 인정 판에 선수 기록 · 계정 번호가 있고,
  **선수 킬 합 = 팀 `kills` · 선수 딜 합 = 팀 `damage_sum` 이 94/94판에서 같다**.
- **기한(배그 경기 기록은 14일 뒤 사라진다)**
  - 이 표의 칸(킬 · 딜 · 사망 · 계정 번호)은 이미 DB 에 있다 → **2 · 3 · 4회 채우기는 기한이 없다.**
  - **1회(9/26 · event 1)는 DB 에 판이 없다**(팀 · 판을 저장하기 전 회차) → PUBG 에서 다시 받아야 한다. **기한 10/10(토) 21:10 KST** 부터 사라지기 시작
    (9/26 21:10 시작 판 + 14일 · 마지막 판은 10/10 23:10). 지금 `/킬내기기록` 은 읽기만(DM) — 1회를 이 표에 넣으려면 저장 길을 따로 연다(오너 결정).
  - 이 표에 없는 값(기절시킨 수 · 어시스트 · 헤드샷 · 생존 시간)을 나중에 넣으려면 2회는 10/19, 3 · 4회는 10/20 까지 PUBG 에서 다시 받아야 한다. 이번에는 넣지 않는다.

### §1.9 종료 시 결과 포스터 자동 게시 — 최종 순위 한 장 (구현 · 첫 장만 · 자동 게시는 꺼진 채 배포)

전에는 `/킬내기집계 게시:true`(오너)가 결과 채널에 순위 글만 올렸고 포스터는 손으로 만들었다. 10/7 지휘 주문으로 순서를 당겨
「대회 종료 시 최종 순위 한 장」만 먼저 만든다(오너 원문 10/7 00:4x 「포스터형식으로 딱 봇이 디코클랜채팅창에 올릴 수 있지 않나?」 「ㅇㅇ 만들자」).
실제로 한 장 올라가는 걸 본 뒤 종류를 늘린다.

- **그리기** — SVG 문자열 → PNG. `@resvg/resvg-js` 2.6.2(새 의존성 · 지휘 승인 10/7 · 리눅스 바이너리 4.2MB · 시스템 라이브러리 없음 · 브라우저 없음).
  - 브라우저를 띄우지 않는 이유 — Railway 7일 실측 메모리 평균 0.11GB · 최고 0.23GB · 한도 8GB 라 용량은 남는다. 그래도 크로미움을 빌드에 싣고
    그릴 때마다 수백 MB 를 대회 중 봇 · 집계와 같이 질 이유가 없다.
  - 이미 있는 sharp 를 쓰지 않는 이유 — 같은 SVG 를 그릴 수는 있었다(실측 +31MB). 그런데 복기 사진 쪽이 보안 때문에 SVG 해독기를
    프로세스 전체에서 막아 둔다(`review-api.cjs` `sharp.block`). 그 막음을 풀지 않는다.
  - 한글 글꼴 — `fonts/Pretendard-ExtraBold.otf` · `fonts/Pretendard-SemiBold.otf`(각 1.6MB · SIL OFL 1.1 · `fonts/OFL-Pretendard.txt`). 파일 경로를 직접 넘긴다(시스템 글꼴 안 씀).
  - 실측(3회 값 · 로컬) — 한 장 0.12~0.16초 · 그리는 동안 메모리 +32~38MB · PNG 약 120KB · 가로 1080.
- **그림에 들어가는 것** — 대회 이름 · 날짜(창 시작 ~ 끝) · 팀 순위(순위 · 팀 · 점수 · 킬 · 판 수 · 시작 보너스) · 개인 킬 상위 5(5위 동점은 같이 · 7줄까지) · MVP.
  - 숫자는 전부 `killrace.players()`(개인 기록 화면과 같은 계산 · 총점은 점수판과 같다)에서 받는다. 포스터가 점수를 다시 세지 않는다.
  - 닉은 인게임(스팀) 닉만. 디스코드 닉 · 계정 번호 · 경매 가격 · 상금은 넣지 않는다.
  - **MVP = 판당 킬 + 판당 딜 100당 1점 1위**(지휘 10/7 — 합계는 많이 뛴 팀이 유리해서 안 쓴다). **그 회차에서 4판 이상 뛴 선수만 후보**다.
    같으면 판당 킬 → 판당 딜 → 판 수 많은 쪽 → 적은 사망 → 닉 순. 아무도 4판이 안 되면 MVP 칸에 「4판 이상 뛴 사람이 없어요」.

### §1.10 스샷 잠정 점수 — 사망 감점 · 버닝 반영 · 음수 표시 (구현 · 서버 #513 · 화면 gmi-clancup #95)

전에는 `killrace-shot.cjs` 가 결과 화면 사진에서 킬 · 딜 · 순위 · 선수별 사망을 읽어 점수판에 「잠정」(킬 · 딜)으로만 붙였다. 감점 · 치킨 · 버닝은 없었다.

- **입력** — 스샷 읽기 결과 + 그 팀 슬롯(감점) + 점수판의 버닝 칸(`boostMode` · `boostSeqs` · `boostAt` · `boostMul`) + 그 팀 확정 판 수(`games`) · 버닝 판을 썼는지(`boostUsed`).
- **점수식** — `killrace.cjs` 한 벌(`scoring` = `baseScore` · `applyBoost` · `SLOT_PENALTY`)을 그대로 쓴다.
  킬 + floor(딜 / 100) + 치킨 8(순위 1) − 사망 슬롯 감점(1번 4 · 2번 3 · 3번 2 · 4번 1). **음수 그대로**.
- **사망**
  - 탈락 화면(순위 2 이상) = **팀 전원 사망**으로 센다. 사망 표시를 못 읽어도 된다 — 전적 판정과 같다(2 · 3 · 4회 탈락 91판 모두 전원 사망 · 10/7 실측).
  - 치킨(순위 1)은 사진의 사망 표시를 읽어야 한다. 한 명이라도 못 읽었거나 죽은 사람의 슬롯을 모르면 점수를 내지 않는다(`basis: "kills"`).
  - 순위를 못 읽었거나 팀 슬롯이 없어도 `basis: "kills"`(짐작하지 않는다).
- **버닝 · 판 순번(5회부터 · §1.13)** — 시각이 필요 없다. 그 팀 미확정 스샷을 시간 순으로 k번째라고 하면 「확정 판 수(`games`) + k」번째 판으로 보고,
  그 순번이 `boostSeqs`(5 · 7)에 들면 곱한다(`boost: 1.5` · 「미정」 아님). 순위를 못 읽은 스샷도 판 하나라서 순번은 하나 차지한다.
  점수판 응답에 `boostMode: "seq"` 가 있을 때만 이 규칙이고, 없으면(옛 서버 · 2 · 3 · 4회) 아래 시각 규칙이다.
- **버닝 · 시각(2 · 3 · 4회)** — 사진만으로는 판 시작 시각을 모른다. 스샷을 올릴 때 그 팀의 마지막 판(`shot.base`)이 이미 버닝 시각 뒤에 시작했으면
  사진 속 판도 확실히 뒤라 곱한다(`boost: 1.5`). 버닝 시각 전에 올린 스샷은 버닝 아님. 그 사이는 `boost: "maybe"` — 곱하지 않고 화면에 「1.5배 미정」.
  그 팀이 이미 버닝 판을 썼으면(확정 판 · 앞 스샷이 확실한 버닝) 버닝 아님 · 앞 스샷이 "maybe" 면 이것도 "maybe".
- **출력** — 점수판 `teams[].shot` 에 칸을 더한다(있던 `n` · `kills` · `damage` · `rank` · `teams` · `dead` · `at` · `players` 는 그대로 — 방송 오버레이가 쓴다).
  - `basis` — "full"(점수를 냄) | "kills"(킬만 반영)
  - `score` — 아직 확정 안 된 스샷 판 점수의 합. 전부 셀 수 있을 때만 · 아니면 null
  - `penalty` — 감점 합(full 일 때만) · `boost` — 배수 | "maybe" | null
  - 총점 · 순위에는 더하지 않는다. 화면은 「스샷 잠정 6위 3킬 −4점」(음수 빨강) · 「스샷 잠정 1위 8킬 딜 1200 (킬만 반영)」.
- **권한** — 공개(점수판 잠정 칸).
- **실측(10/7 · 3회 · 4회 사진)**
  - 3회 28장 중 27장 일치(순위 · 팀 킬 · 딜 ±2) · 1장은 1킬 오독(9 대 10)
  - 4회 비교 가능한 15장 중 14장 일치 · 1장은 다른 팀 · 다른 판 사진
  - 이 규칙의 잠정 점수 = 확정 점수: 버닝 판 3개를 뺀 38판 중 36판(틀린 2판은 오독 사진). 사망 표시를 읽을 수 있었던 사진은 46장 중 1장
  - 킬은 플러스인데 실제 판 점수가 음수였던 사진 11장 — 이 절이 고친 것

### §1.13 버닝 — 시각제 폐지, 팀마다 5 · 7번째 판 1.5배 (5회 10/8부터 · 오너 OK 10/7)

오너 원문(2026-10-07 새벽): 「버닝을 바꾸자 평균적으로 6판이상하니까 5판, 7판 두 판만 적용되도록 시간제말고」.
지금(2 · 3 · 4회): 진행자가 버닝 시각을 넣고, 그 시각 뒤 **처음 시작한 판 하나**가 1.5배다. 시계를 봐야 하고 시각을 잘못 넣으면 끝이다.

- **방식은 대회 설정 한 칸** — `ops_state` `killrace:event:<id>` 에 `boostMode`(`"time"` 시각 · `"seq"` 판 순번) · `boostSeqs`(순번 목록 · 기본 `[5, 7]`)를 **더한다**.
  기존 칸(`boostAt` · `boostMul`)은 지우지 않는다.
  - 설정에 `boostMode` 가 없으면 **회차 번호로 정한다**: 1 ~ 4회 = `"time"`(지난 회차 설정은 손대지 않는다 · 읽는 결과가 종전과 같다),
    **5회부터 = `"seq"` · `[5, 7]`**. 그래서 5회 줄을 만들면(경매가 보너스만 저장해도) 시각 입력 없이 판 순번 버닝이 켜진다. 적힌 값이 있으면 그것이 먼저다.
  - 순번 목록은 정수 1 ~ 50, 겹침 없이 오름차순으로 읽는다. 비었거나 깨졌으면 `[5, 7]`.
- **순번 = 점수판 판 번호(`seq`)** — 팀마다 시작 시각 순으로 매긴 **인정 판** 번호다. 무효(진행자 표시) · 인원 미달 · 시간 밖 · 모드 제외 판은 순번에 안 센다.
  **이탈 판은 순번을 차지한다.** 집계는 순번을 먼저 매기고 버닝 판을 고른 뒤 점수를 낸다(`killrace.cjs` 6단계).
- **배수** — 그 판의 판 점수 전체 × `boostMul`(1.5). 음수 판도 1.5배, 소수점은 지금처럼 0 에서 먼 쪽(10.5 → 11 · −4.5 → −5). 계산식(`applyBoost`)은 그대로다.
- **★ 이탈 판(오너 확인 중 · 지휘 기본값)** — 5번째(7번째) 판이 이탈이면 −10 고정, 배수 없음, **그 버닝은 그냥 지나간다**(다음 판으로 안 넘어간다).
  버닝 표시(`flags.boost`)는 그 판에 남겨 두어 이탈을 풀면 1.5배가 다시 붙는다. 이 규칙은 `boostTargets` 한 곳에 모았다.
  「이탈 판은 순번에서 빼고 다음 판이 5번째」로 바뀌면 이탈 표시 · 해제가 **다른 판의 배수를 옮겨야** 해서 `setLeave` 가 그 팀 판을 다시 세야 한다
  (코드 두 곳 + 시험 · 한 줄 변경으로 끝나지 않는다). 「이탈 판도 1.5배(−15)」로 바뀌면 `finalScore` 한 줄이다.
- **6판 이하로 끝난 팀은 7번째 버닝이 없다.** 4판 이하면 버닝이 없다.
- **판 무효 표시 · 해제 = 바로 한 번 집계** — 앞 판이 무효가 되면 뒤 판 순번이 당겨져 버닝 판이 옮겨 간다. 대회가 끝나 1분 집계가 멈춘 뒤에도
  바로 맞도록 진행자 「이 판 무효」가 표시할 때도 한 번 센다(종전: 해제할 때만).
- **진행자 「버닝 시각」** — 판 순번 회차에서는 받지 않는다: 409 `boost_by_seq`(저장해도 안 쓰이는 값이라 · 저장 · 바꾼 기록 없음). 시각 방식 회차는 종전 그대로(저장 + 바꾼 기록 · §1.7).
  - §1.7 대회 설정도 같다(검수 41차 ②): **`eventCreate` 는 버닝 시각을 받지 않는다**(새 대회는 5회부터라 늘 판 순번 · 넣으면 409 `boost_by_seq` · 대회를 만들지 않음).
    `eventTimes` 는 판 순번 회차면 `boostAt` 이 비어 있을 때만 창을 고치고, 값이 있으면 409 `boost_by_seq`. 진행자 화면은 판 순번 회차에서 「1.5배 판 시작」 칸을 숨긴다.

**응답 모양(더하기만 · 옛 칸 유지)** — `GET /api/killrace/board`

| 칸 | 시각 방식(2 · 3 · 4회) | 판 순번(5회부터) |
|---|---|---|
| `boostMode` (새) | `"time"` | `"seq"` |
| `boostSeqs` (새) | `[]` | `[5, 7]` |
| `boostAt` | 버닝 시각(ms) | **`null`** — 옛 화면이 「1.5배 판까지 N분」을 잘못 띄우지 않게 |

**스샷 잠정(§1.10 · Draft #513)** — 판 순번 회차면 시작 시각이 필요 없다. 미확정 스샷을 시간 순으로 k번째라고 하면
「확정 판 수 + k」번째 판으로 보고, 그 순번이 `boostSeqs` 에 들면 잠정 점수에 1.5배를 곱하고 `shot.boost: 1.5`(「미정」 아님)로 낸다.
시각 방식 회차는 종전 `"maybe"` 규칙 그대로다. 총점 · 순위에는 지금처럼 더하지 않는다.

**화면이 고칠 곳(gmi-clancup · 반장 룰 화면 — 지휘가 나른다)**

- 오버레이(`killnaegi-overlay.html` · `-v2`) 바닥 줄 — `boostAt` 이 `null` 이면 지금은 버닝 안내가 안 나온다. `boostMode === "seq"` 일 때
  「5 · 7번째 판 1.5배」(숫자는 `boostSeqs` · `boostMul` 로 그린다)와 팀별 `nextBoost`(「다음 판 1.5배」)를 띄운다.
- 점수판(`killnaegi-board.html`) — 「1.5배 판까지 N분 / 지금 시작하는 판은 1.5배」 칩과 역전 칸 「1.5배 판이 남아 있어요」는 시각 방식에서만 쓰고,
  판 순번이면 팀마다 `boosts`(5번째 ✓ · 7번째 남음 · 이탈로 지나감)를 보여 준다. 판별 줄의 `base ×1.5` 표시는 그대로 맞다.

### §1.14 늦은 블루칩 부활 — 4페이즈부터 부활 비행기를 타면 그 판 −10 (5회 10/8부터 · 오너 OK 10/7)

오너 원문(2026-10-07 새벽): 「블루칩은 (일겜 경쟁 둘다)3페이지까지만 살릴 수 있도록」 · 「아예금지 위반 시 -10 … 살리는 건 3페이지 몇번째 비행기 까지만 4페이지때 살아나지 않도록」.
지휘 실측(2 · 3 · 4회 74판 텔레메트리 · 일반전): 부활 비행기 탑승(`LogVehicleRide` · `vehicle.vehicleId` 에 `Redeploy`)은 경기 시작(`LogMatchStart`) 기준
241 · 391 · 541 · 691 · 841 · 991 · 1141 · 1291초(150초 간격)이고, `LogPhaseChange` 3페이즈는 781초 · 4페이즈는 961초에 시작했다(에란겔 · 미라마 · 태이고 같음).
그래서 841초 비행기(다섯 번째)까지 허용, 991초(여섯 번째)부터 위반이다. 우리 참가자 부활 탑승 38건 중 16건이 여섯 번째 이후였다.

- **판정** — 그 판 텔레메트리에서 **`LogPhaseChange` 의 `phase` 가 4 인 첫 사건 시각**(4페이즈 시작)을 본다. 그 판 출전 명단의 우리 팀 선수(그 판에 뛴 교체 선수 포함)가
  **그 시각 이후(같은 시각 포함)에 부활 비행기에 탔으면 위반**이다. 초가 아니라 그 판의 페이즈 사건을 보므로 맵 · 모드가 달라도 맞는다.
  - 부활 비행기 = `LogVehicleRide` 중 `vehicle.vehicleId` 에 `redeploy`(대소문자 무시)가 든 것. 시작 비행기는 걸리지 않는다.
  - 4페이즈가 오기 전에 끝난 판은 위반이 없다(`ok`).
- **위반 판 = 이탈과 같은 길** — 판 점수 −10 고정, 배수 없음(버닝 판이면 그 버닝은 지나간다 · `boosts` 의 `passed`), **판 순번은 차지한다**(#519 의 이탈 처리와 같다).
  동점 기준(킬 · 치킨 · 딜) · 개인 기록 · 포스터 · 개인 누적 지표(§1.11)에서도 이탈 판처럼 뺀다. 이탈 표시와 겹쳐도 −10 한 번이다.
- **다섯 번째 비행기까지의 부활은 지금처럼** — 살아서 끝내면 사망 감점 없음(블루칩 치킨 규칙 · 사망 판정 코드는 안 바꾼다).
- **텔레메트리를 못 읽은 판** — 위반 아님 · `revive.state = "unknown"`(「확인 못 함」). 대회 중에는 다음 집계에서 다시 읽는다
  (실패한 판은 2 · 4 · 8 · 16분 간격으로 쉬었다가 · 한 번 집계에 최대 8판). 대회 끝 + 45분에 자동 집계가 멈춘 뒤에도 못 읽었으면 「확인 못 함」으로 남고 점수는 그대로다.
- **대회별 설정** — `ops_state` `killrace:event:<id>` 에 `lateRevive` 를 **더한다**.
  - `"penalty"` = 위반이면 −10(기본) · `"flag"` = 의심 표시만 하고 점수는 그대로(진행자가 보고 이탈 −10 으로 처리하는 반자동) · `"off"` = 안 본다.
  - 설정에 없으면 **회차 번호로 정한다**: 1 ~ 4회 = `"off"`(지난 회차 기록 · 점수 그대로) · **5회부터 = `"penalty"`**. 적힌 값이 있으면 그것이 먼저다.
  - `revivePhase`(기본 4 · 정수 2 ~ 9)로 기준 페이즈를 바꿀 수 있다.
  - 경쟁전은 비행기 · 페이즈 시각이 다를 수 있고 아직 실측이 없다. 판정은 페이즈 사건 기준이라 맞을 것으로 보지만, 첫 경쟁전 회차는 `"flag"` 로 돌려 실측을 보고 정하기를 권한다.
  - 진행자 화면 「대회 설정」에서 바꾼다(진행자 동작 `lateRevive` · 바꾼 기록에 남김 · 바꾸면 바로 한 번 집계해 점수를 다시 센다).
- **텔레메트리를 읽는 때** — 지금 자동 집계는 사망 판정을 deathType 으로 해서 텔레메트리를 안 읽는다.
  `lateRevive` 가 `"off"` 가 아닌 회차는 **자동 집계에서도 인정 판마다 한 번 텔레메트리를 읽는다**(기존 스트리밍 해석기 · 매치당 한 번 · 원본은 버리고 필요한 사건만 ·
  결과는 `deaths.telemetry` 에 저장해 다음 집계는 다시 안 받는다). 사망 판정은 그대로 deathType 이다(점수식은 안 바뀐다).
  - 뽑는 사건이 둘 늘어난다: 우리 선수의 `LogVehicleRide`(부활 비행기만) → `players[계정].redeploys[시각…]` · `LogPhaseChange` → `phases[{ phase, at }]`.
  - PUBG 텔레메트리는 분당 조회 한도(10회)와 따로다(CDN 파일). 판당 원본 수 MB(압축)를 흘려 읽어 메모리는 거의 안 는다.

  | 칸 | 키 | 규칙 |

  | 주 포지션 | `position` | `오더` · `돌격` · `저격` · `서포트` 중 하나 · 필수 |

- **저장** — `ops_state` 새 줄 `killrace:applyintro:r2` = `{ [신청 id]: { position, style, ambition, cardName, at, saves } }`.

  **기존 신청자가 소개를 채워도 명단 · 계좌 값은 그대로다.** 표 · 칸을 새로 만들지 않아서 **DDL 이 없다**(SQL §69 불필요 · env 없음).

  `no_position` · `no_style` · `no_ambition` · `long_ambition` · `long_card_name` · 저장 안 함) 신청과 함께 저장한다. 다른 키(옛 `weapons` 등)는 버린다.

  - `{ action: "introEdit", id, intro, by }` — 4칸 검사(본인 저장과 같은 오류 코드) 뒤 그 사람 소개를 바꾼다. 줄에 `by` 를 남기고 `saves` 를 1 올린다.
    진행자 조회의 `intro.by` 로 「진행자 ○○ 님이 고침」이 보인다(공개 응답에는 없다). 본인이 나중에 다시 저장하면 `by` 는 사라진다.
  - `{ action: "introClear", id, by }` — 그 사람 소개 줄을 지운다 → 「안 채운 사람」으로 돌아가고 본인이 「내 신청」에서 다시 채운다(마감 전까지). 이미 비어 있어도 200.
  - 응답은 진행자 조회와 같은 모양(`adminView`). 로그 `[killrace-apply] intro_host_edit|intro_cleared order=<n>`(이름 · 글은 안 남긴다).
  - 화면 = `killnaegi.html?host=1` 「선수 소개 모아 보기」 줄마다 「고치기」 · 「비우기」. 바꾸는 사람 이름은 점수판과 같은 자리(`kn_host_by` · 이 기기)에 기억한다.
- **진행자 조회의 전적 줄** — 줄의 `tier`(경쟁전 티어 글자) · `avgDamage` · `kda` 를 그대로 보여 준다. **신청할 때 전적 조회(`computeBPI`)로 한 번 받아 둔 값**이라 새 조회 · env · 키가 없다.
  기준 시즌 = 지금 시즌(기록이 없으면 지난 시즌) · 평딜 = 경쟁전 판 수가 넉넉하면 경쟁전 평딜, 아니면 일반전 평딜 · KDA = PUBG 시즌 통계의 KDA((킬 + 어시스트) ÷ 데스 — K/D 가 아니다).
  화면 · 응답 표기는 「KDA」(`kda`)만 쓴다 — 「K/D」로 쓰지 않는다(지휘 10/7 · KDA 값 그대로 쓰기로 정함).
- **공개 응답** — `GET /api/killrace/apply`(키 없음) 줄에 `intro: { position, style, ambition, cardName }` **네 칸만** 더한다
  (카드 이름이 비었으면 `null` — 공개 응답에서는 디스코드 닉으로 채우지 않는다 · 소개가 없으면 `intro: null`). 맨 위에 `positions`(포지션 넷) · `styles`(성향 셋)도 더한다.
  디스코드 닉 · 계좌 · 신청 id 는 공개 응답 어디에도 없다(시험이 응답 글자 전체에서 찾는다).
  점수판(`/api/killrace/board`) · 개인 기록(`/players`)은 신청 줄을 읽지 않아서 이번에 바뀌지 않는다.
- **디스코드 신청 카드 · 로그** — 카드는 그대로(디스코드 닉 · 인게임 닉 · 티어). 로그는 `[killrace-apply] intro_saved order=<n> saves=<n>` 한 줄(닉 · 글은 안 남긴다).
- **안 바뀌는 것** — 정원 · 대기 · 마감 · 중복 규칙 · 계좌 경계(오너 JWT 전용) · 점수 · 집계 · 버닝 · 상금 계산.
- **검증** — 시험(가짜 저장소 · 운영 DB 에 시험 신청을 넣지 않는다): 새 신청 4칸 → 진행자 조회에 그대로 · 기존 신청자 「내 신청」 → 새 칸만 저장 →
  명단 · 계좌 줄 글자가 저장 전후 같다 · 공개 응답에 디스코드 닉 · 계좌 · id 없음. 운영은 배포 전후 명단 · 계좌 줄 md5 를 대조한다
  (10/7 06시 KST 스냅샷: 명단 4건 · 계좌 4건).

  - `killrace:applykind:r2` = `{ [신청 id]: { kind, at, saves, by? } }` — 본인(새 신청 · 「내 신청」) 또는 진행자(`by`)가 쓴다.

- **공개 응답** — **참가 구분을 싣지 않는다**(검수 44차 · 10/7 — 「누가 레슨생인지」라 진행자 응답에만 둔다 · 줄마다 `kind` 도 이름표 목록도 없음).

- **디스코드 신청 카드** — 「구분」 칸 하나 더(레슨생 · 클랜원 · 외부 참가 · 안 고름). 로그는 `applied … kind=<키|->` 한 단어 더.
- **후원 줄(은근하게)** — 신청 칸 맨 아래 본문보다 작고 옅은 글씨 두 줄: 「상금은 이무리 사비 방지턱에서 나가요」 · 「보태고 싶은 분은 디스코드로 알려 주세요」

- **화면(gmi-clancup `killnaegi.html`)** — 참가 구분 칸은 신청서 맨 위(필수 · 안 고르면 「참가 구분을 골라 주세요」). 외부 참가를 고를 때만 바로 아래 참가비 칸이 열린다

  「내 신청」에도 같은 구분 칸 · 참가비 칸 — 저장 하나로 구분과 소개를 같이 보낸다(구분 필수). 공개 「신청한 사람」 명단에는 구분이 없다(공개 응답에도 없다).
- **오너 확정(10/7 · 지휘 전달 · 원문 「환불 문장 빼기」 「바로 보여주기」 「계좌 없이 두기」)** — ① 환불 문장은 폼에 두지 않는다
  ② 대기 순번 외부 참가자도 입금 안내를 바로 본다(지금 그대로) ③ 후원 줄은 계좌 없이 「보태고 싶은 분은 디스코드로 알려 주세요」 — 공개 페이지에 계좌번호를 적지 않는다(설정 줄 안 넣음).
- **안 바뀌는 것** — 정원 · 대기 · 마감 · 중복 규칙 · 계좌 경계(오너 JWT 전용) · 점수 · 집계 · 버닝 · 상금 계산 · 기존 신청 값.
- **검증** — 시험(가짜 저장소 · 운영 DB 에 시험 신청을 넣지 않는다): 구분 셋 · 틀린 값 400 · 키 없는 옛 요청은 받고 「안 고름」 ·
  외부 참가 → 진행자 조회 `feeUnpaid` 에 뜨고 체크하면 빠짐 · 레슨생은 `not_external` · 공개 응답에 참가 구분 · 입금 여부 · 진행자 이름 · 디스코드 닉 · 계좌 · id 없음 · 대기 순번 외부 참가자는 대기 표시와 같이 · 취소하면 빠짐 ·

- **같은 사람 합치기** — `ops_state` `killrace:people` = `{ merge: { "<옛 계정>": "<기준 계정>" } }`. 옛 계정 판을 기준 계정 판으로 센다(티어표와 같다).
  계정 번호는 이 설정 줄(DB)에만 둔다 — 코드 · 문서에 적지 않는다. 처음 한 쌍은 지휘 10/9 지시(티어표의 두 닉 = 한 사람)로 세션이 넣었다.
- **자격** — 누적 **20판 이상** + 기준 시각에서 **30일 안에 1판 이상**(가장 최근 판의 시작 시각).
- **점수** — 자격자끼리 판당 킬 · 판당 딜의 z 점수(모집단 표준편차)를 낸다. `score = 0.5 × z(판당 킬) + 0.5 × z(판당 딜)` · 소수 셋째 자리.
  모집단은 **그때 자격자 전원**이다(자격 없는 사람은 평균 · 편차에 안 들어간다). 편차가 0 이면 그 z 는 0.
  같은 점수면 판 수 많은 순 → 판당 킬 → 닉(늘 같은 순서).
- **묶음** — `group` = `"1"`(1위) · `"2-4"`(2 ~ 4위) · `"5-10"`(5 ~ 10위). 오너 원문은 「6~10등」이지만 5위가 빠지므로 5 ~ 10위로 읽는다(지휘 10/9).
- **갱신(스냅샷)** — 계산 결과를 `ops_state` `killrace:leaderboard` 에 저장하고 응답은 저장본을 낸다(역할 봇이 갱신 사이에 같은 값을 본다).
  - 매주 **수요일 09:00 KST**(그 시각 뒤 첫 tick) · 회차가 끝난 뒤 한 번(`window_end` + 45분 — 마지막 판 확정을 기다린다 · §1.12 와 같은 여유).
  - 서버 tick 1분마다 확인 · 저장본이 없으면 첫 GET 이나 첫 tick 에서 만든다. 다시 계산하는 일은 위 두 때뿐이다.
- **응답** — `GET /api/killrace/leaderboard`
  `{ at, basis: { reason: "weekly"|"event"|"first", eventId? }, rules: { minGames: 20, recentDays: 30 }, eligible, list: [{ rank, group, key, ign, games, kpg, dpg, score }] }`
  - `kpg` 소수 둘째 자리 · `dpg` 정수 · `key` = §1.11 과 같은 불투명 키.
  - **`account_id` 는 진행자 키(`x-admin-key`)로 부를 때만 줄마다 붙는다** — §1.11 처럼 공개 응답에 계정 번호를 싣지 않는다. 클랜CODE 봇은 진행자 키로 부르고
    계정 번호 → 디스코드 회원은 등록계(`clan_registry`) 쪽에서 잇는다. 새 env 없음.
  - 표가 없으면 503 `table_missing` · 그 밖은 500. 60초 캐시 없음(저장본 한 줄 읽기).
- **검산(10/9 · 운영 DB 읽기만)** — 자격자 16명. 1위 · 2 ~ 4위 · 5 ~ 10위 열 명이 지휘 미리 계산과 순서까지 같다(닉은 문서에 적지 않는다).
  모듈을 운영 줄(선수 판 704 · 판 181)에 그대로 돌려 확인했다. 지휘 계산과 판 수가 다른 곳은 번외 회차의 늦은 부활 −10 판 1판뿐이다
  (그 팀 선수의 판 수가 1씩 적다 · §1.11 과 같은 규칙으로 뺀다 · 순위는 같다). 5회 늦은 부활 판 3개는 「표시만」 처리라 그대로 센다.
  (모집단을 「판 기록이 있는 사람 전원」으로 잡으면 7 · 8위가 바뀐다 — 자격자끼리가 맞다.)
- **안 바뀌는 것** — 점수판 · 회차 점수 · 보정 · 개인 누적 지표(§1.11) · 경매 티어표.

### §1.19 상금 원장 — 적립(+) · 지급(−) · 선수 지급 요청 → 오너 지급완료 (10/9 오너 OK · 지휘 주문 · DDL §73)

오너 원문(10/9): 「어플에 지급버튼 눌러서 나한테 알람오고 내가 지급하면 완료버튼눌러서 알람 기록 되도록」 · 「컷머니 적립된 거 중에서 55,000원 4회차까지 상금중」.
지금은 상금이 말과 DM으로 오가서 누가 얼마를 받았는지 흩어져 있다. 한 표에 모은다. **앱은 돈을 움직이지 않는다 — 송금은 오너가 직접 한다.**

- **표** `killrace_prize_ledger`(DDL §73 · 더하기만) — 한 줄 = 적립 하나 또는 지급 하나.
  - 공통: `platform` · `account_id`(사람 키 = PUBG 계정 · 닉이 바뀌어도 같은 사람) · `ign`(적을 때의 닉 · 보이기용) · `amount`(원 · 늘 양수) · `memo`(200자) · `entered_by`(「오너」「경비(세션)」).
  - **적립** `kind = accrue` — 회차(`event_id`) · 사유(「1등」「MVP」) 필수. 같은 회차 · 같은 사람 · 같은 사유는 한 줄.
  - **지급** `kind = payout` — 상태 `requested`(요청됨) → `paid`(지급완료) 또는 `cancelled`(요청 취소). 회차는 비워도 된다(여러 회차 적립분에서 나간 돈).
    `source` = `app`(선수 요청) · `owner`(오너가 요청 없이 바로 지급). 시각 칸: `requested_at` · `request_notified_at`(오너 알림) · `paid_at` · `paid_notified_at`(선수 알림) · `cancelled_at`.
  - **지우지 않는다.** 바꿀 수 있는 것은 「요청됨 → 지급완료 / 취소」 한 번, 빈 알림 시각 채우기 한 번, 메모뿐이다(방아쇠가 막는다).
  - **계좌 · 실명 · 디스코드 id 는 이 표에 없다.**
- **잔액** — 보기 `killrace_prize_balance`: 사람별 `accrued`(적립 합) · `paid`(지급완료 합) · `requested`(열린 요청) · `balance = accrued − paid` · 가장 최근 닉.
  적립 줄을 오너 확정 뒤에 넣으므로, 그 전에 적은 지난 지급은 잔액이 잠시 0 밑으로 보인다(아래 첫 줄).
- **흐름(앱 화면은 별도 주문)**
  1. 선수 — 앱 「지급 요청」. 열리는 조건 = 잔액 ≥ **30,000원**(10/7 「3만원 채우면」 · 설정 `ops_state` `killrace:prize` `{ payoutMin }` · 코드 기본값도 30000)
     + 열린 요청 없음(사람마다 하나 · DB 유일 색인). 요청 금액 = 그때 잔액 전부. → `requested` 줄 · 오너에게 디스코드 알림 → `request_notified_at`.
  2. 오너 — 앱 밖에서 직접 송금 → 「지급 완료」 → `paid` · `paid_at` · 선수에게 알림 → `paid_notified_at`. 오너가 「요청 취소」를 누르면 `cancelled`.
  3. 요청 없이 바로 보낸 돈은 오너가 `source = owner` · `paid` 줄로 적는다.
  - 선수 본인 확인 · 알림 경로 · 화면은 앱 계약(#534)에서 정한다. 이 절은 표와 상태 규칙까지다.
- **처음 넣은 줄(10/9 · 세션 · 지휘 주문 · 오너 OK)** — 33줄(적립 31 · 지급 2).
  - 지급 2줄(지금까지 실제로 돈이 나간 사람은 둘뿐 · 오너 10/9): 55,000원(회차 비움 · 메모 「2~4회 적립 상금 중 지급 · 오너 진술 10/9」) ·
    30,000원(회차 비움 · 메모 「2회 상금 · 오너 진술 10/9」) · 둘 다 `paid` · `source = owner`.
  - 적립 23줄(2 ~ 4회 · 오너 10/9 「1 ~ 4회차까진 공평분배」): 회차 상금을 1등 팀 몫 · 2등 팀 몫으로 나누고 팀 안에서는 똑같이 나눈다.
    2회(20만) = 1등 팀 12만 · 2등 팀 8만 → 1인 30,000 / 20,000 · 3회 · 4회(각 16만) = 1등 팀 10만 · 2등 팀 6만 → 1인 25,000 / 15,000.
    사유는 「1등 팀」「2등 팀」. 회차 합 200,000 · 160,000 · 145,000(4회 2등 팀 한 자리 15,000 은 오너 귀속 — 줄 없이 메모만).
  - 검산: 적립 505,000 − 지급 85,000 = 남은 420,000 · 18명 중 잔액 0 은 위 지급 2명 · 잔액 있는 선수 16명(적립액 그대로).
  - **1회(9/26 · 대승배 1회)는 원장 밖에서 정산 끝** — 그때 전부 지급했다(오너 10/9 「1회는 그때 다 줬어」). 원장에 줄을 넣지 않는다.
  - **5회(대승배 · 10/8 · 상금 30만) 적립 8줄** — 팀 안은 티어 순 비율(상금 포스터 · 오너 10/8): 1등 팀 24만 = 1번 100,000 · 2번 70,000 · 3번 50,000 · 4번 20,000,
    2등 팀 6만 = 같은 비율 25,000 · 17,500 · 12,500 · 5,000. 티어 순서 = 회차 팀 등록의 슬롯 1 → 4(사망 감점 슬롯을 티어 높은 순으로 배정 · 팀장 = 팀 최고 티어).
    같은 티어 둘이면 두 자리 몫을 합쳐 반씩(2등 팀 1 · 2번 = 1.5티어 동률 → 21,250 씩). 사유는 「1등 팀 1번」처럼 자리 번호까지.
    1등 팀 1 · 2번은 경매 기록에 팀장 티어가 없어 확인 뒤 넣었다(지휘 10/9 「팀장 = 팀 최고 티어 · 동률 아님」).
  - 검산(5회까지): 적립 31줄 805,000 − 지급 85,000 = 남은 720,000.
- **3만 원 미만 잔액** — 15,000 · 20,000 · 25,000 인 선수는 다음 상금이 쌓일 때까지 요청 버튼이 잠긴다. 앱 화면은 잠긴 이유
  (「3만 원부터 요청할 수 있어요」와 지금 잔액 · 남은 금액)를 같이 보여야 한다(화면 주문 때 문구 확정).
- **§68(#520 · `event_reward_ledger` · 현금 · 포인트 두 갈래 · 실행 전)과의 관계** — 같은 일을 하는 두 번째 표가 되지 않게, **상금 원장 실행본은 이 표(§73)** 다.
  §68 의 포인트 전환 · 사용은 아직 오너 미확정이라 실행하지 않는다. 포인트가 확정되면 이 표에 더하기만으로 칸 · 종류를 늘리는 쪽으로 다시 쓴다(지휘 판단).
  §1.17(#542 · `killrace_pool_ledger`)은 클랜 적립금(들어온 돈 · 나간 상금 총액) 장부라 사람별 원장인 이 표와 다르다.
- **안 바뀌는 것** — 트레이너 정산 · `payments` · `payouts` · 점수 · 보정. 이 표는 그 어느 것과도 외래 키 · 함수로 잇지 않는다(`event_defs` 만).

### §1.22 사망 감점 = 팀 안 티어 순서 (10/10 오너 OK · 7회 = event 8 부터 · 소급 없음)

- **바뀐 것** — 죽은 사람 감점(−4 · −3 · −2 · −1)을 슬롯 번호가 아니라 **그 팀 4명을 티어로 줄 세운 순서**로 붙인다. 1등 −4 · 2등 −3 · 3등 −2 · 4등 −1(3인 팀이면 −4 · −3 · −2).
  슬롯 번호는 표시용이다. 이유(오너): 1티어가 부계정이 없으면 본계정으로 들어오는데, 번호가 아니라 실제 실력 순서로 감점이 붙어야 공정하다.
- **티어를 찾는 순서** — ① 팀 등록 줄 `event_teams.members[].tier`(원장이 그때 정한 신규 티어 · DDL 없음) → ② 티어표 `ops_state 'killrace:tiers'`
  `{ list: { 닉소문자: { ign, tier, rank } } }`. 같은 티어면 전체 순위(rank · 작은 수가 위) → 그래도 같으면 슬롯 순.
- **한 명이라도 티어가 없으면 그 팀은 슬롯 순서**(종전과 같다). 교체 선수(/킬내기교체)는 그 슬롯의 감점을 물려받는다(종전과 같다).
- **회차 기본값** — 회차 설정 `penaltyBy` 가 있으면 그것(`"tier"` · `"slot"`), 없으면 event id 8 이상 `"tier"` · 그 전 `"slot"`. 6회까지 점수는 그대로다.
- **저장 · 표시** — 판 줄 `flags.penBySlot`(슬롯 → 감점)에 그 판에 쓴 표를 남긴다. 사망 무효 해제 · DM 카드 「사망: 닉(n번 −k)」도 이 표를 쓴다. board 응답 `penaltyBy`.
- **티어표 갱신** — 지휘가 준 목록을 세션이 `killrace:tiers` 에 넣는다(10/10 · 47명 · 2 ~ 6회 기준 · 6회 봇판 제외). 계정 합치기(`killrace:people`)는 닉이 바뀐 사람을 표에 같은 닉으로 넣어 맞춘다.
- **스샷 잠정 점수(§1.10)** 는 슬롯 감점 그대로다(잠정이라 확정 집계가 고친다).

### §1.23 회차 설정 — 신청 폼 회차 · 마감 · 이름 · 모드 (10/10 지휘 · 코드 대신 설정)

- **설정 줄** — `ops_state 'killrace:applycfg'` = `{ round: "r8", closeAt: "2026-10-16T11:30:00Z", label: "7회", needAccount: false, mode: "low" | "high" }`.
  신청 API 가 요청마다 읽는다(재시작 · 배포 없음). 없거나 깨진 칸은 코드 기본값(6회 값 · r6 · 10/9 23:00).
- **round** = 신청 명단 줄 이름(`killrace:apply:<round>` 등 다섯 줄). 회차마다 새 이름을 쓰면 지난 회차 명단은 그 줄에 그대로 남는다.
- **공개 응답** `GET /api/killrace/apply` 에 `closeAt` · `closed` · `label` · `mode` · `needAccount`. 화면(클랜CODE)은 회차 · 마감 글자를 이 값으로 그린다.
- **모드** — `low`(저티어 판 · 1번은 부계정 권장 · 없으면 본계정 OK) · `high`(고티어 판). 정하는 건 원장. 집계 쪽은 회차 설정 `killrace:event:<id>` 의 `mode` 로 board 에 실린다.
- **운영 시간(오너 10/10)** — 금요일만 · 신청 마감 20:30 · 드래프트 20:30 ~ 20:55 · 경기 21:00 ~ 23:00(23:00 전에 시작한 판만) · 23:30 안에 끝. **22:00 이후 시작하는 회차는 만들지 않는다**(늦으면 사람이 없어 봇방이 잡힌다 — 6회 사고).

### §1.24 개인 스텟에서 봇 킬 · 봇 딜 빼기 (10/10 오너 「개인 스텟만 · 7회부터」 · 계약 먼저)

- **범위** — 개인 기록만: 회차 선수 표(`/players`) · 개인 누적(§1.11) · 리더보드(§1.18) · 티어 집계 · 자리별 MVP(§1.9). **팀 점수는 게임 공식 기록 그대로**(킬 · 딜 · 순위 점수 안 바뀜).
- **언제부터** — event id 8(7회) 이상인 판만. 6회 이전은 소급하지 않는다(6회 봇판은 §1.21-부록대로 판 통째 무효).
- **식** — 판마다 선수별로 `사람 킬 = 공식 kills − (combat 중 k = kill · a = 본인 · v 가 "ai." 로 시작)`,
  `사람 딜 = 공식 damage − (combat 중 k = dmg · a = 본인 · v 가 "ai." 로 시작 의 d 합)`. 음수면 0. combat = `event_match_telemetry`(§67 · 판별 상세 채우기가 저장).

### §1.21 1회(9/26 · event 1) 개인 기록 살리기 — 일회용 · 진행자 키 · 더하기만 (10/9 지휘 급함 · 배그 원본 10/10 저녁 만료)

> (배그 오류 원문을 남기던 서버 로그 줄도 모듈과 함께 없어졌다). 아래는 기록용이다. 4팀 1회 계정은 `killrace:people` 합치기로 지금 계정에 묶었다.

1회는 3인 스쿼드라 팀 줄(`event_teams`)이 없어 판 기록이 0줄이다. 팀마다 DB 에 계정이 있는 「기준 선수」만 주면, 그 사람의 창 안 매치에서
**같은 로스터(같은 팀 번호)** 의 팀원을 그대로 읽는다(닉 명단 18개가 필요 없다). 모듈 `killrace-backfill.cjs`.

- **길** — `POST /api/killrace/backfill/admin` · 진행자 키(`x-admin-key`)만 · 몸 `{ eventId: 1, teams: [{ name: "1팀", anchors: ["닉", "닉|옛닉"], exclude: ["닉"] }], dryRun }`.
  **`eventId` 는 1 만** 받는다(그 밖은 400 `bad_event` — 2회부터는 팀 줄이 있어 같은 판이 다른 팀 이름으로 겹쳐 들어가 리더보드가 부풀어요).
  `exclude`(팀마다 4개까지 · 대소문자 무시)는 대타처럼 그 팀 기록에 넣지 않을 닉 — 슬롯 · 선수 줄 · 팀 킬 · 딜 합에서 빠지고 응답 `excluded` 에 찍힌다.
  **기본은 미리 보기**(`dryRun` 을 빼거나 `true`) — 쓰지 않고 팀별 판 수 · 찾은 팀원 닉 · 순위 · 경고만 돌려준다. `{ dryRun: false }` 일 때만 쓴다.
- **기준 선수 → 계정** — DB 에서만 찾는다(지난 회차 선수 판 → 클랜 등록계 → 회차 팀 명단 · 대소문자 무시). 응답에 계정 번호는 없다.
- **판 인정** — 회차 창 [시작, 끝)(event 1 = 9/26 21:10 ~ 23:10 KST)에 **시작한 일반전 스쿼드**(`official` · `squad`/`squad-fpp`)만. 기준 선수가 둘 이상인 팀에서
  둘이 서로 다른 로스터로 들어간 판은 뺀다(경고 한 줄).
- **쓰는 것(더하기만)** — `event_matches`(판 하나 = 팀 하나 · `seq` = 팀 안 시작 순서 · `win_place` · 킬 합 · 딜 합 · 사망 슬롯 · `score` · `penalty` **비움** ·
  `flags.source = "backfill_r1"`) · `event_match_players`(로스터 2 ~ 4명 · 킬 · 딜 · 사망 · 슬롯 = 팀에서 처음 본 순서, 기준 선수 먼저).
  같은 `(회차, 팀, match_id)` 는 두 번 들어가지 않는다(먼저 읽어 건너뜀 + 넣을 때 겹치면 무시).
- **안 하는 것** — 점수 · 슬롯 감점 · 팀 순위 · 상금(1회 순위는 9/27 정정 공지가 정본). 쓴 판은 `seq` 가 있어 개인 누적(§1.11) · 리더보드(§1.18)에 들어간다.
- **실패 시** — 배그 한도 429 `rate_limit` · 키 없음 503 · 동시에 두 번 409 `busy`. 매치 하나가 실패하면 경고 한 줄 뒤 다음 판.
  응답은 코드만 싣는다 — 배그 오류 원문(주소에 계정 번호가 들어갈 수 있다)은 서버 로그에만 남긴다. **쓰기 중 실패가 뜨면 다시 부르지 않는다**(보고 뒤 DB 로 확인).
- **되돌림** — `delete from event_matches where event_id = 1 and flags->>'source' = 'backfill_r1'`(선수 줄은 외래 키로 같이 지워진다 · B 구간이라 지휘 확인 뒤).
- **치우기** — 실행 · 검증 끝나면 다음 배포에서 require 한 줄 · createBackfill 블록 · `killrace-backfill.cjs` · 시험 파일(`scripts/killrace-backfill.test.cjs` · `package.json` check 두 줄) 제거.

### §1.11 개인 누적 지표 — 계정 기준 (구현 · Draft PR)

- **입력** — `GET /api/killrace/career?events=2,3,4`. 회차 번호 묶음(쉼표 · 50개까지 · 비우면 전부)이고, 숫자가 아니면 400 `bad_events`.
- **재료** — §1.8 `event_match_players` + `event_matches`(인정 판 = `seq is not null and not leave_flag`). 판 무효 · 이탈 · 제외 판은 안 센다(점수판 · 개인 기록과 같다).
  점수 계산식은 쓰지 않는다.
- **출력** — `{ events, minGames: 10, players: [{ key, ign, games, kills, damage, deaths, killsPerGame, damagePerGame, teamTopKills, events, sample }], updatedAt }`
  - `key` — 계정 번호 대신 내는 불투명 키(16자). SESSION_SECRET 에서 이 용도로만 뽑은 키의 HMAC 이라 키에서 계정 번호를 되찾을 수 없다.
    같은 계정은 늘 같은 키다(SESSION_SECRET 을 바꾸면 키도 바뀐다 · 포털 불투명 id · 이어 읽기 표지와 다른 키).
  - `ign` — 그 계정의 가장 최근 판 닉. 닉을 바꿔도 한 사람으로 이어진다.
  - `killsPerGame` 은 소수 둘째 자리, `damagePerGame` 은 정수, `damage` 는 내림.
  - `teamTopKills` — 그 판 우리 팀에서 킬이 가장 많았던 판 수(공동 1등 포함 · 0킬 판은 안 센다).
  - `sample` — `games` 10 이상이면 "ok", 미만이면 "low"(표본 부족). §1.3 팀장 추천이 이 표시를 본다.
  - 정렬 — 표본 있는 사람 먼저 → 판당 킬 → 판당 딜 → 판 수 → 닉(같은 값이면 늘 같은 순서).
- **권한** — 공개. 닉 · 숫자 · 불투명 키만 싣는다(계정 번호 · 디스코드 · 실명 없음). 60초 캐시.
- **실패 시** — 표가 없으면 503 `table_missing`(§66 실행 전 환경), 그 밖은 500. 줄이 많으면 1000줄씩 이어 읽고 5만 줄에서 멈춘다(로그 한 줄).
- **실측(10/7 · 2 · 3 · 4회 · 읽기만)** — 36명(10판 이상 19 · 표본 부족 17) · 두 회차 넘게 뛴 사람 17 · 판마다 닉이 달랐던 계정 1(한 사람으로 이어짐) ·
  선수 판 492 · 킬 814 · 팀 내 킬 1등 146번(공동 포함).

### §1.12 판별 상세 기록 저장 — DDL §67 (10/7 02:3x KST 실행) · 채우는 코드 `killrace-detail.cjs`

배경: PUBG 는 매치 기록과 텔레메트리(판 안의 모든 사건)를 **14일** 뒤 지운다. 2회(10/5)는 **10/19 저녁**, 3 · 4회(10/6)는 **10/20 저녁**부터 사라진다.
지금 DB 에는 선수별 킬 · 딜 · 사망만 있다(§1.8). 기절시킨 수 · 어시스트 · 헤드샷 · 생존 시간 · 이동 거리 · 위치 · 교전 기록은 없다.

- **두 갈래로 받는다**
  1. 매치 참가자 통계(매치 조회 한 번) → `event_match_player_detail`(선수 × 판 한 줄 · §1.8 표와 같은 키 · 외래 키)
     — 기절시킨 수 · 어시스트 · 헤드샷 킬 · 최장 킬 거리 · 살린 수 · 생존 시간 · 걷기 · 탈것 · 수영 거리 · 회복 · 부스트 · 팀킬 · 킬 순위.
  2. 텔레메트리(우리 팀 선수 것만 추린다) → `event_match_telemetry`(팀 × 판 한 줄 · jsonb)
     — 위치: `LogPlayerPosition`(10초마다) → 선수별 `[초, x, y, z]`(m 정수)
     — 교전: `LogPlayerTakeDamage`(우리 선수가 주거나 받은 것만) · `LogPlayerMakeGroggy`(기절) · `LogPlayerKillV2`(킬 · 사망 · 무기 · 거리) · `LogPlayerRevive`
- **받는 방법(구현 · `killrace-detail.cjs`)** — 서버의 기존 스트리밍 해석기(`fetchTelemetry` · 요소를 하나씩 읽어 메모리가 거의 안 는다)에 상세 수집기를 끼워 쓴다.
  - **1분마다 매치 하나**(서버 tick). 대상은 끝 + 45분이 지난 회차의 판(`event_match_players` 줄이 있는 팀 × 판)이고, **회차 번호 → 시작 시각 순**이다(2회 원본이 먼저 사라진다).
  - **대회 시간에는 쉰다** — 어느 회차든 시작 30분 전 ~ 끝 + 45분 안이면 그 차례를 건너뛴다(자동 집계 · PUBG 조회와 겹치지 않게).
  - 매치 조회(`/matches` · 분당 한도 밖)로 참가자 통계를, 텔레메트리로 위치 · 교전을 받는다. 한 매치에 우리 팀이 둘이면 한 번 받아 팀마다 나눠 쓴다.
  - **끝난 판 = `event_match_telemetry` 줄이 있는 팀 × 판**(표가 진실 · 따로 상태를 두지 않는다 · 재시작해도 이어서 한다). PUBG 키는 서버(Railway env)에만 있다.
  - 끄기: `ops_state` `killrace:detail` = `{ off: true }`(없으면 켜짐).
  - 위치 = 경기 시작부터 초 · m 정수 · 10초에 하나. 교전 = 우리 선수가 주거나 받은 피해(0 딜 제외 · 블루존 포함) · 기절 · 킬 · 살림(`d` 딜 · `hs` 헤드샷 · `dist` m).
  - 로그: 매치마다 `[killrace-detail] match_ok event · match · teams · detail · bytes · events · positions · combat · json(KB) · ms` 한 줄(첫 줄이 한 판 실측이다).
- **용량 어림** — 실측은 첫 실행 때 한 판으로 먼저 잰다(아래 순서 2). 이 세션 환경에서는 api.pubg.com 이 막혀 있어 미리 못 쟀다.
  - 참가자 통계: 줄당 약 200B × 492줄 = 약 0.1MB.
  - 텔레메트리(우리 팀만): 위치 = 선수 4 × 30분 / 10초 = 최대 720점 × 약 25B ≈ 18KB, 교전 = 판당 약 100~300건 × 약 100B ≈ 10~30KB → 팀 · 판당 약 30~50KB.

  - 받는 양: 텔레메트리 원본은 판당 수 MB(압축)이고 서로 다른 판 수만큼 받는다. 스트리밍이라 서버 메모리는 거의 안 는다.
- **순서**

- **권한** — 저장 = 서버. 읽기 = 진행자 · 오너(계정 번호가 들어 있다). 공개 화면에는 §1.11 처럼 닉 · 숫자만 가공해서 낸다.

  오너 = `MRI_OWNER_ID`(사이트 로그인 토큰이든 킬내기 앱 토큰이든). **새 env 없음** — 알림은 이미 있는 봇 DM 이다.
- **DDL** — 상태 · 알림 시각 칸은 §73 원장에 이미 있다(`status` requested · paid · cancelled · `request_notified_at` · `paid_notified_at`).
  본인 확인 표시만 **§74 `killrace_prize_verifications`**(새 표 하나 · 더하기만 · §70 다음에 실행)로 더한다.

| 길 | 누구 | 하는 일 |
|---|---|---|
| `GET /api/killrace/me/prize` | 선수 | `{ linked, ign, key, accrued, paid, balance, min: 30000, canRequest, reason, short, open, lines[] }` |
| `POST /api/killrace/me/prize/request` | 선수 | 잔액 **전액** 한 건 → `requested` 줄 · 오너 알림 → `{ ok, request{ id, amount, at }, notified }` |
| `GET /api/killrace/prize/admin` | 오너 | `{ min, pending[], recent[], players[], totals{ accrued, paid, requested } }` |
| `POST /api/killrace/prize/admin` | 오너 | `{ action: "paid" \| "cancel", id, memo? }` → `{ ok, id, status, at, notified }` |
| `POST /api/killrace/prize/admin` | 오너 · 진행자 키 | `{ action: "verify" \| "unverify", key, by? }` → `{ ok, key, verified, by?, at? }` (본인 확인 · 아래) |

- **요청이 열리는 조건**(`canRequest`) — 계정 연결됨 + **본인 확인됨** + 열린 요청 없음 + 잔액 ≥ **30,000원**(10/7 오너). 아니면 `reason` 하나(이 순서로 먼저 걸리는 것):
  `not_linked` → `open_request` → `not_verified` → `below_min`. `verified`(참 · 거짓)와 `short`(3만 원까지 남은 돈)는 늘 같이 실어서 화면이 둘 다 보일 수 있다. 요청 금액은 늘 그때 잔액 전부다.
  같은 사람의 열린 요청은 DB 유일 색인이 한 번 더 막는다(두 번 눌러도 한 줄 · 409 `open_request`).
- **화면 문구(ui-copy · 돈 문구라 느낌표 · 이모지 없음 · 화면 주문 때 확정)**
  - 켜짐: 「지급 요청」 칩 · 잔액 표시. 미만: 「3만 원부터 요청할 수 있어요 (지금 21,250원)」. 요청 중: 버튼 대신 「요청 접수됐어요」.
  - 본인 확인 전: 「본인 확인이 끝나면 요청할 수 있어요」(지휘 10/9 문구).
  - 연결 전: 「스팀 닉을 연결하면 내 상금이 보여요」(앱 내 계정 화면으로).
  - `lines[]` = 회차별 적립 줄(회차 이름 · 사유 · +금액) · 지급 줄(요청 · 완료 · 취소 · 시각) · 최근 것 먼저.
- **오너 알림**(봇 DM · 오너에게만 · 운영진 말투) — 「[킬내기 상금] 지급 요청 · 닉 · 금액」 · 회차별 적립 · 요청한 디스코드 이름 · 「송금한 뒤 「지급 완료」를 눌러 줘」.
  보내지면 `request_notified_at` 을 적는다. 봇이 없거나 DM 이 막혀도 **요청은 남고** 오너 목록에 「알림 안 감」으로 보인다.
- **지급 완료**(오너만) — 요청됨인 줄만 `paid` · `paid_at` 으로 바꾼다(두 번 눌러도 한 번 · 이미 끝난 줄 409 `not_requested` · 없는 줄 404).
  바꾼 뒤 선수에게 DM 「킬내기 상금 n원 지급 완료됐어요. 기록은 킬내기 앱 「내 상금」에서 볼 수 있어요」 → `paid_notified_at`.
  **되돌리기 없음** — 잘못 눌렀으면 메모로만 바로잡는다(§73 방아쇠가 상태를 되돌리지 못하게 막는다). 취소(`cancel`)는 요청됨일 때만 · 잔액은 그대로라 다시 요청할 수 있다.
- **오너 목록의 `players[]`** — 선수마다 선수 화면과 **같은 판정**(`balance` · `canRequest` · `reason` · `short`)을 싣는다. 선수로 로그인하지 않고도 화면 상태를 확인하는 실측 길이다.
- **본인 확인(지휘 10/9 결정)** — 앱의 스팀 연결은 닉으로 PUBG 계정을 찾아 먼저 연결한 회원에게 묶는다(앱 계약 §4). 남의 닉을 먼저 잡아 요청하는 일 자체를 막으려고,
  **진행자가 「확인」을 누르기 전에는 지급 요청이 잠긴다**(돈 관련 기록이라 사람 손 한 번).
  - 누가 누르나: 오너(`MRI_OWNER_ID`) 또는 진행자 키(`x-admin-key` · 지휘가 정한 관리자 · `by` 이름 필수 · 없으면 400 `need_by`). 그 밖은 403 `host_only`.
  - 무엇을: 오너 목록 `players[].key` 로 고른 선수 — 그 계정을 **지금 연결한 회원**에게 확인 줄 하나(§74 · 회원 번호 + 플랫폼 + 계정 · 누가 · 언제).
    연결한 회원이 없으면 409 `not_linked`. 같은 회원은 한 줄(다시 누르면 새로 적는다). `unverify` 는 그 줄을 지운다(다시 잠긴다).
  - **확인은 회원 · 계정 한 쌍에 묶인다** — 회원이 다른 계정으로 다시 연결하면 줄의 계정과 달라져 저절로 다시 잠긴다. 회원을 지우면(탈퇴) 같이 지워진다.
  - 판단 재료: 오너 목록 `players[].member` = `{ name(디스코드 표시 이름), linkedAt, verifiedBy, verifiedAt }`(디스코드 번호는 없다).
    오너 알림에도 요청한 디스코드 이름이 실린다.
- **응답 경계** — 계정 번호 · 디스코드 번호는 어디에도 없다(사람 = `key` · 스팀 닉). 표가 없으면 503 `table_missing`.
- **먼저 있어야 하는 것** — ① 조각 A(#537) 머지 + DDL §70 실행(회원 표 · 로그인 표지) ② DDL §74(본인 확인 · §70 바로 다음) ③ §73(✅ 10/9)
  ④ 화면 `killrace/`(클랜CODE · 지휘 10/9). ①②가 없으면 선수 길은 503, 오너 목록(`GET prize/admin`)은 §73 만으로 돈다(회원 칸은 비어 나온다).
- **클랜CODE 화면용 목록(이 절만 보면 된다)**
  - 로그인 · 회원 · 연결 = 앱 계약 `docs/killrace-app-api.md` §2 ~ §5(`/api/auth/login?intent=killrace` · `GET /api/killrace/me` · `POST /me/consent` · `/me/link`).
  - 선수 「내 상금」 = `GET /api/killrace/me/prize` → 줄 목록 + `canRequest` · `reason` · `verified` · `short` 로 칩 · 안내 문구를 고른다.
  - 「지급 요청」 = `POST /api/killrace/me/prize/request`(몸 없음) → 409 면 `error.code` 가 위 `reason` 과 같은 값.
  - 오너 「지급 대기」 = `GET /api/killrace/prize/admin`(`pending[]` · `recent[]` · `players[]` · `totals`) → 「지급 완료」 `POST prize/admin { action: "paid", id }` · 「요청 취소」 `{ action: "cancel", id }`.
  - 진행자 「본인 확인」 = `POST prize/admin { action: "verify", key, by }`(진행자 키) · 오너는 `by` 없이.
  - 공통 오류: 401 `login_required` · 403 `not_member` · `owner_only` · `host_only` · 409 위 이유들 · `not_requested` · 404 `not_found` · 503 `table_missing` · 429 `rate_limited`.
- **실측(시험 줄을 운영 DB 에 넣지 않는다)** — 오너 목록의 `players[]` 로: 1위 선수(잔액 80,000) 본인 확인 뒤 `canRequest: true`(확인 전 `not_verified`) ·
  민준팀 1번(21,250) `short: 8,750` · 지급 대기 0건 · 잔액 0 인 선수(지급완료 이력 있음) `canRequest: false`.
