## 6. 🔴 원장 대시보드 「이번 달」 카드에 쓸 때

### 6-1. `gross` 를 쓰면 안 된다
`computeTrainer` 의 `gross = max(0, lessonAccrued + consultPay − paidOut)` 에서
`lessonAccrued` 는 **미정산분만**(= 9월)인데 `paidOut` 은 **전기간 payouts** 다.
실측 기지급 현태 4,461,900 · 준구 2,857,100 이라 **두 트레이너 모두 `gross = 0`** 으로 떨어진다.
→ 카드는 `payable`(+ 당월 상담 가산)을 쓴다. `gross` 는 누적 정산용이다.

### 6-2. floor100 은 (학생 × 진행 트레이너)마다 걸린다
`computeStudent` 가 쌍마다 버린 뒤 `computeTrainer` 가 더한다. **합계에 한 번 거는 게 아니다.**
이 문서의 이전 판이 합계에 한 번 걸어서 적혀 있었고(현태 870,500 · 준구 209,700) 바로잡았다.

### 6-3. 상담 가산은 당월분만 · 진행자 기준
월 필터와 `handler_id` 귀속이 엔진에 들어갔다. 진행자가 비어 있는 행은 가산되지 않고 로그에 남는다.

## 7. 🔴 이번에 드러난 계산 오류 3건 — 전부 고쳤다

판정을 반영하려고 엔진을 고치다 실측으로 드러났다. 셋 다 **지급액이 틀리던 것**이다.

1. **판수 정정(음수 행)이 지급에서 안 빠졌다.** `g <= 0` 을 통째로 건너뛰어 판수만 줄고
   지급액은 그대로였다. 실측: 미정산 −6판 1건 때문에 현태 지급이 6판만큼(약 15,300원) 부풀어
   있었다 — 판수는 319인데 지급은 325판 기준이었다.
2. **이진 부동소수점 오차로 100원이 깎였다.** 90,000/21판 단가로 6판 × 0.70 은 정확히 18,000 인데
   JS 가 17999.999999999996 을 내고 `floor100` 이 17,900 으로 버렸다. 9월에만 2명 · 200원.
   버리기 전에 1e-6 자리에서 반올림하도록 고쳤다.
3. **Postgres `numeric` 나눗셈 오차** — 내가 SQL 로 뽑아 보고한 867,400 이 100원 낮았다.
   단가를 유한 자리로 자른 탓이다. 정확값 **867,500**.

세 건 모두 `scripts/settlement.test.cjs` 가 고정한다. 특히 3번은 **나눗셈 없이 정수 분수로**
다시 계산해 대조하므로, 앞으로 어떤 경로로 계산하든 이 오차가 다시 들어올 수 없다.

## 8. 상담만 받은 사람 — `prospect` 상태값 (실행 완료)

9/20 상담 20,000 은 명부에 없는 사람이라 결제행을 만들 수 없었다(`payments.student_id` 가 NOT NULL + FK).
**10/1 부터 레벨 테스트 신규가 전부 이 경우**라 오너 OK 를 받아 상태값을 더했다(§39 · B 구간).

### 왜 기존 값으로 안 되나
| | 문제 |
|---|---|
| `active` | 로스터·잔여·수강생 수에 레슨생과 섞인다 |
| `paused` | 「수강하다 멈춘 사람」이라 뜻이 다르다 — 재개 대상 목록이 오염된다 |
| `done` | 수료다 — 수료 목록이 틀어진다(§38 과 같은 논거) |

### 집계 규칙 (오너 확정)
**로스터·잔여·수강생 수에서 제외 · 매출·상담 가산에는 포함.** 코드에서 지키는 곳:

| 자리 | 처리 |
|---|---|
| 트레이너 포털 로스터 | 이미 `status in (active,paused)` 라 제외됨 — 변경 없음 |
| `computeTrainer.student_count` | `prospect` 제외 |
| 승급 후보(`liveStu`) | `prospect` 제외 — 아직 수업을 안 한 사람이다 |
| 잔여 독촉 | 이미 `active` 한정 — 변경 없음 |
| 패널 `is_prospect` | 상태값이 정본, 뷰의 파생 계산보다 먼저 본다 |
| `/수강생등록` 동명 경고 | **`prospect` 를 포함**한다 — 상담만 받고 등재된 사람이 레슨을 시작하면 그 행을 `active` 로 올려야지 새 행을 만들면 안 된다 |

전환(`prospect` → `active`)은 **사람이 한다.** 첫 등록이 생겼다고 자동으로 올리지 않는다 —
자동 승격은 되돌리기가 어렵고, 등록이 취소되는 경우를 구분하지 못한다.

## 9. 예약은 닫혔는데 기록이 없는 건 — 매일 밤 점검

§37 은 이미 `done` 인 예약에 **아무것도 하지 않는다**. `done` 의 이유가 「자정 넘겨 다른 날짜로 이미
등록」일 수도 있어 자동으로 판수를 넣으면 두 번 빠지기 때문이다. 그래서 「예약 done · 그날 기록 없음」
짝은 **아무 코드도 못 고치는 상태**로 남고 판수가 0회 빠진다.

실측(2026-09-28): 1건. head 는 `done` 인데 span tail 은 `booked` 로 남아, 어느 코드 경로도 만들 수
없는 짝이었다 — 사람이 콘솔에서 상태만 바꾼 흔적이다.
