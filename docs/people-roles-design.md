## 1. 결론 먼저 (비유)

- **사람은 이미 한 사람이다 — 이름표만 세 장이다.** 수강생 명부 · 킬내기 회원표 · 등록계가 모두 **디스코드 계정 번호**를 열쇠로 쓰고,
  세 표 모두 그 번호가 **유일**하다(수강생 명부는 유일 인덱스가 이미 있다). 그래서 「사람」 표를 새로 만들 필요 없이
  **서버가 로그인한 디스코드 번호로 세 표를 한 번에 읽으면** 그게 「1줄」이다.
- **앱은 문 하나, 방 둘.** 앱(app.mriacademy.gg) 로그인은 하나 · 들어오면 「레슨」 방과 「클랜」 방이 칩 두 개로 갈린다.
  가진 방만 열리고, 클랜원끼리는 킬내기 기록 · 티어 · 클랜 등급만 보인다. 돈 · 판수는 본인 · 운영진만.
- **1단계는 DDL 0.** 서버 코드(경비) + 앱 화면(반장)만으로 연다. 여러 스팀 계정 · 킬내기 계정 합치기를 표로 옮기는 건 2단계(초안만 · §7).

## 3. 사람 기준 — 디스코드 번호 하나로 묶는다

### 3.1 왜 새 「사람」 표를 만들지 않나 (AI 판단 · 근거)

- 세 표가 이미 같은 열쇠(디스코드 번호)를 쓰고 셋 다 유일하다 → 조인 한 번이면 1줄이 된다. 새 표를 만들면 **네 번째 이름표**가 생기고,
  어느 쪽이 정본인지 다시 정해야 한다(운영 원칙 「적는 곳 하나」와 어긋난다).
- 클랜 등급의 정본은 디스코드 역할이다. DB 에 복사하면 역할을 바꿀 때마다 두 곳이 어긋난다(옛 시즌 값 하드코딩 사고와 같은 모양) → **복사하지 않고 읽을 때 본다**(봇 조회 · 10분 기억 · 킬내기 `guildFor` 와 같은 방식).
- DDL 이 없으면 「코드가 DDL 보다 먼저 배포」 사고가 생길 자리가 없다. 1단계를 Draft 대기 없이 연다.

### 3.2 「1줄」의 모양 (서버 안에서만 · 응답에는 번호가 없다)

```
사람(디스코드 번호 D) =
  lesson : students where discord_id = D and merged_into is null          → 0 또는 1줄 (유일 인덱스)
  killrace: killrace_members where discord_id = D                          → 0 또는 1줄 (유일)
  registry: clan_registry where discord_id = D order by season desc limit 1 → 0 또는 1줄
  grade  : GmI 길드에서 D 의 역할 중 가장 높은 것 G > m > I               → 'G' | 'm' | 'I' | null
  accounts(스팀): students.pubg_account_id · student_accounts(현재) · killrace_members.account_id · clan_registry.account_id
                  + killrace:people 합치기 → 같은 사람의 계정 목록(겹치면 하나)
```

- **역할(앱 방) 판정**
  - `lesson` 방 = `students` 줄이 있다(상태 무관 · prospect 는 「레벨 테스트 뒤 열려요」 상태로).
  - `clan` 방 = GmI 길드에서 **G · m · I 역할 중 하나**를 가졌다.
    길드 가입만으로는 안 된다 — 레슨생도 `/수업등록` 때문에 GmI 길드에 들어와 있어서, 가입만 보면 레슨생 전원이 클랜원으로 잡힌다.
    (킬내기 참가 구분 `kindOf` 는 「길드 가입만」 + 레슨 우선이라 지금은 문제가 가려져 있다. 클랜 방은 역할 기준으로 따로 본다 — 킬내기 판정은 이 설계가 바꾸지 않는다.)
  - 둘 다 아니면 지금처럼 `/pending`(연결 신청 · 레벨 테스트 신청 · 클랜 안내).
- **봇이 못 보면**(재기동 직후 · 길드 조회 실패) `grade: null` · `clan` 방은 「잠깐 확인 중이에요」로 닫아 둔다(모름을 「아님」으로 읽지 않는다 · 기억하지 않고 다음 요청에 다시 본다).

### 3.3 등록계는 어디에 쓰나

- 등록계는 「시즌 전적 계정 + 본인 명의」다. 클랜 방 입장 조건으로 쓰지 않는다(미등록 클랜원이 있다 — `/등록계검수` 대상).
- 클랜 방 「내 정보」에 **등록 여부 · 시즌 · 명의 확인 여부**만 보여 주고, 미등록이면 「/등록계로 등록해 주세요」 안내(창구).

| 킬내기 개인 기록(판 · 킬 · 딜 · 점수 · 회차) | ✅ | ✅ | ✅ | 이미 공개 길(`/api/killrace/career`) — 불투명 키 |

| 클랜 등급 G · m · I | ✅ | ✅ | ✅ | 디스코드에서 이미 보이는 값 |
| 스팀 닉 | ✅ | ✅(킬내기 동의한 사람만) | ✅ | 킬내기 동의 글 「공개되는 것」 |
| 등록계(시즌 · 명의 확인) | ✅ | ❌ | 오너(`/등록계현황`) | 명의는 공개 값이 아니다 |

| 디스코드 번호 · PUBG 계정 번호 · 실명 · 계좌 | ❌(응답에 없음) | ❌ | 종전대로 | 킬내기 계약 §1 과 같다 |

- **클랜원 목록에 오르는 사람** = 클랜 역할 + **킬내기 동의(회원 줄)** 둘 다 있는 사람만. 동의 안 한 클랜원은 목록에 없다(본인 화면은 열린다).
  길드 전원을 한꺼번에 읽어 목록을 만들지 않는다 — 멤버 대량 조회는 1회성 명령에서만 한다는 기존 원칙(`registry-audit-dm.md` §1-1)을 지킨다.

## 5. 이미 섞인 사례로 검증 (10/10 실측 · 오늘 경비가 등록한 둘)

### #110 — 레벨 테스트 → 직강 (레슨생으로 들어온 사람)

| 항목 | 지금 |
|---|---|
| 명부 | active · 담당 있음 · 직강 등록 1 · 결제 2 · 수업 기록 0 · 별칭 2 |
| 디스코드 연결 | **없음** — 연결 신청 1건 대기(10/9) |
| PUBG 계정 | 없음(플랫폼만 steam) |
| 킬내기 · 등록계 | 없음 |

- 지금: 앱에 들어오면 `/pending`. 연결 신청이 승인되면 `scope:"student"` → 레슨 방(직강 카드 · 회차). 클랜 역할을 받으면 같은 로그인에 클랜 방이 붙는다 — **옮기거나 합칠 게 없다.**
- 확인할 것(경비): 대기 중인 그 연결 신청 줄에 `student_id` 가 이미 채워져 있다. 봇이 신청을 만들 때(`server.js` linkIntake)는 이 칸을 비우고,
  승인이 실패해 되돌릴 때(`link-approve.cjs` release)도 비운다 → 정상 흐름에서는 대기 줄에 값이 없다. 승인 버튼은 상태만 보고 값을 덮어써서 승인 자체는 돈다. 누가 언제 채웠는지만 확인.

### #111 — 킬내기 참가자 → 레슨 (클랜 쪽에서 들어온 사람)

| 항목 | 지금 |
|---|---|
| 명부 | active · 담당 있음 · 결제 1 · 수업 기록 0 · 별칭 2 |
| 디스코드 연결 | **없음** — 연결 신청도 없음 |
| PUBG 계정 | 명부 닉은 있음 · **계정 번호 칸 비어 있음** |
| 킬내기 | 같은 닉이 킬내기 2개 회차 팀 줄에 있음 · 그 닉의 계정 번호 1개 · 킬내기 앱 회원은 아님 |
| 등록계 | 같은 닉 없음 |

- 지금: 앱에 들어오면 `/pending`. 클랜 역할이 있으면(이 설계 뒤) 클랜 방만 먼저 열린다 → 「스팀 연결하면 킬내기 기록이 보여요」.
  레슨 방은 「이미 레슨 받고 있어요」 → 연결 신청 → 승인되면 두 방.
- 막히는 곳 둘:
  1. 명부의 PUBG 계정 번호가 비어 있어서 **레슨 쪽 「내 성장」 · 첫 레슨 랭크 기록이 킬내기 계정과 안 이어진다.** → 킬내기 팀 줄의 계정 번호로 명부 대표 계정을 채운다(경비 · 연결 정정 · 금액 · 판수 안 바뀜 · §8 목록 2).
  2. 디스코드가 연결되기 전까지는 두 기록이 「닉이 같다」로만 이어진다. 닉 일치는 자동 연결의 근거로 쓰지 않는다(별칭 원칙) → 계정 번호 채우기는 **사람이 확인한 뒤**.

**검증 결론** — 두 사례 모두 「디스코드 연결 하나」만 끝나면 구조상 한 줄로 묶인다. 막힌 곳은 구조가 아니라 **연결이 안 된 데이터**(24/77)다.
→ 클랜 방을 열면 클랜원 쪽 연결은 「로그인만 하면 된다」로 풀리고, 레슨 쪽은 지금 연결 신청 흐름을 그대로 쓴다.

  홈 화면에 깔린 아이콘 이름(웹 앱 manifest 이름)과 스토어 등록 이름은 밖으로 보이는 이름이라 **오너 확인 뒤**(§9 확인 못 한 것 1).
- 로그인 화면 문구(제안 · 반장이 ui-copy 로 최종): 제목 「GmI · MRI」 · 한 줄 「디스코드로 들어오면 클랜 기록과 레슨이 한곳에 모여요」 · 버튼 「디스코드로 시작하기」.

## 7. 2단계 초안 — 사람별 PUBG 계정 표 (실행 보류 · 번호는 경비가 실행 때 매김)

1단계는 계정을 네 곳(명부 대표 · 수강생 계정 이력 · 킬내기 회원 · 등록계) + 합치기 줄에서 **읽어서** 모은다. 계정이 여러 개인 사람이 늘거나
킬내기 합치기(`killrace:people`)가 10줄을 넘으면 표 하나로 옮긴다. 아래는 그때 쓸 **더하기만** 초안이다 — 1단계 코드는 이 표에 기대지 않는다.

```sql
-- (초안 · 실행 보류) 사람별 PUBG 계정 — 한 사람 여러 계정 · 출처 기록. 디스코드 번호 또는 수강생 #번호 중 하나는 있어야 한다.
create table if not exists public.person_accounts (
  id          bigint generated always as identity primary key,
  discord_id  text   check (discord_id is null or discord_id ~ '^[0-9]{5,25}$'),
  student_id  bigint references public.students(id),
  platform    text   not null check (platform in ('steam', 'kakao')),
  account_id  text   not null check (account_id ~ '^account\.[0-9a-f]{32}$'),
  is_main     boolean not null default false,
  source      text   not null check (source in ('student', 'killrace', 'registry', 'merge', 'staff')),
  note        text,
  created_by  text,
  created_at  timestamptz not null default now(),
  constraint person_accounts_owner check (discord_id is not null or student_id is not null)
);
create unique index if not exists person_accounts_account on public.person_accounts (platform, account_id);   -- 계정 하나 = 사람 하나
create index if not exists idx_person_accounts_discord on public.person_accounts (discord_id) where discord_id is not null;
create index if not exists idx_person_accounts_student on public.person_accounts (student_id) where student_id is not null;
alter table public.person_accounts enable row level security;                                                 -- 정책 0 = service_role 만
-- 실행 뒤: notify pgrst, 'reload schema';  · REQUIRED_SCHEMA 에도 넣는다(CLAUDE.md 「3곳」)
```

- 채우기(그때 · 더하기만 · 새 표에 줄 추가): 명부 대표 계정 → `student` · 킬내기 회원 → `killrace` · 등록계 최신 시즌 → `registry` · `killrace:people` → `merge`.
  같은 계정이 두 사람에게 걸리면 유일 인덱스가 막는다 → 넣지 않고 목록으로 지휘에게.
- 옮긴 뒤에도 `killrace:people` 는 지우지 않는다(지우기 = 오너 OK 구역). 읽는 쪽만 새 표로 바꾼다.

## 9. 확인 못 한 것 · 오너 손

1. **홈 화면 아이콘 · 플레이 스토어 이름** 「GmI · MRI」로 바꿀지(밖에 보이는 이름) — 오너 확인. 앱 안 머리는 그 전에 바꿔도 된다.
2. **클랜 등급 이름** — 역할은 G · m · I 셋으로 읽었다(env 이름 · `/등록계검수` 정렬 실측). 화면 표기를 「G」 「m」 「I」 그대로 둘지, 다른 이름(예 등급명)이 있는지는 오너만 안다. 서버는 `"G" | "m" | "I"` 를 내리고 이름은 앱 상수로 둔다.
3. **킬내기 앱(gmi-clancup · 10/7 확정 B1)과의 관계** — AI 판단: 킬내기 신청 · 경매 · 점수판은 **그대로 gmi-clancup** 에 둔다(외부 참가자 · 방송 · 대회 시간 배포가 수강생 앱에 걸리지 않게).
   수강생 앱 클랜 방은 같은 서버 · 같은 회원 표 · 같은 키를 **읽고**, 신청은 킬내기 앱으로 연결한다. 클랜 방에서 스팀 연결 · 동의를 하면 킬내기 앱에서도 같은 회원이다(디스코드 번호가 같다).
   나중에 신청까지 앱으로 옮길지는 v2 때 다시 본다.
4. **클랜 방의 미성년** — 킬내기 동의는 만 14세 미만을 받지 않는다(앱 계약 §4.1 · 오너 결정 대기). 클랜 방 본인 화면(등급 · 등록계)은 동의 없이 열리고, 기록 공개 · 목록 등재만 동의 뒤다. 보호자 동의 길(§33)과 잇는 건 오너 결정 뒤.
