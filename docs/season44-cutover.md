# 44시즌 전환 절차 · G드컵 시즌4 BPI 기준 고정 (2026-08-25 · 관제탑 긴급 지시)

> GmI 트랙 소관 · 카지노 휴면 중 **관제탑 승인 경유 대행분**. 소관은 GmI에 남는다.
> **env·DDL은 Level 0(오너 실행)** — 이 문서는 절차·수치·문구 발행이고 실행은 오너다.
> 실측은 전부 실DB·실코드 직접 조회(2026-08-25).

## 0. 🔴 즉시 보고 3건 — 지시 전제와 실측이 다르다

### (1) `BOT_REGXFER` env는 **코드에 존재하지 않는다**

```
grep 'process.env.BOT_' server.js  →  BOT_PAYREQ 단 1건
grep 'BOT_REGXFER'      server.js  →  0건
```

**전환 승인 게이트는 이미 배포돼 있고**(PR #247 · 8/22 머지 · `queueRegistryTransfer`),
플래그가 아니라 **`registry_transfer_requests` 테이블 존재 여부**로 켜진다:

| 상태 | 동작 |
|---|---|
| 테이블 **있음** | 전환이 pending 큐로 — 오너 DM 승인/반려 버튼, 7일 만료 |
| 테이블 **없음**(현재) | **degrade — 종전대로 즉시 교체** + 하루 1회 오너 경고 DM |

**→ 「BOT_REGXFER 가동」의 실체는 env 설정이 아니라 §20 DDL 실행이다.**

### (2) §20 DDL **미실행** — 게이트가 지금 꺼져 있다

```
information_schema.tables → registry_transfer_requests : 없음
```

**지금 이 순간 등록계 전환은 승인 없이 즉시 교체되고 있다.** 공지가 나가기 전에
DDL을 실행해야 공지 내용(「전환은 승인 후 반영」)과 실제 동작이 일치한다.

### (3) ⚠️ 시즌 번호가 이미 밀려 있을 가능성

| 소스 | 값 |
|---|---|
| `PUBG_CUR_SEASON_NUM` 코드 기본값 | **41** (`process.env.PUBG_CURRENT_SEASON_NUM \|\| "41"`) |
| `clan_registry` 실측 | **42시즌 38명** (전량) |
| `registry_history` 실측 | **42시즌 51행** (전량) |
| 관제탑 인식 | **43시즌 운영 중** (9/9에 43→44) |

`/등록계`는 등록 시점의 `PUBG_CUR_SEASON_NUM`을 season에 찍는다. DB가 전량 42라는 것은
**현재 env가 42**이거나 42시즌 이후 등록이 없다는 뜻이다. 관제탑 인식(43)과 어긋나므로
**9/9 갱신 전에 현재 값부터 확인해야 한다** — 43을 건너뛰고 42→44로 가면 43시즌 등록·심사
이력이 영구 공백이 된다. **오너 확인 요청: Railway `PUBG_CURRENT_SEASON_NUM` 현재 값.**

## 4. 마감 검사(9/2)는 **아직 코드에 없다**

`GMI_NEXT_SEASON_START`를 설정해도 **현재 구현은 그 값을 읽지 않는다**(grep 0건).
즉 9/2가 지나도 전환 신청이 그대로 접수된다.

**선택지 (판정 요청)**

| 안 | 내용 | 비용 |
|---|---|---|
| **A(권고)** | `queueRegistryTransfer` 진입부에 마감 검사 ~10줄 추가 — 미설정 시 검사 생략(fail-open) | 코드 1곳 · 봇 재기동 |
| B | 코드 미변경 · 마감 후 들어온 pending을 오너가 반려로 정리 | 0 (운영 부담) |

A 채택 시 이 세션이 구현한다(GmI 대행 · 관제탑 승인 필요). **마감이 승인 게이트를
대체하는 게 아니므로** 미구현이어도 승인 절차 자체는 정상 작동한다.

## 5. G드컵 시즌4 BPI 기준 시점 고정

### 5-1. ⚠️ `GDCUP_CURRENT_SEASON`은 env가 아니라 **코드 상수**다

```
server.js:3836  const GDCUP_CURRENT_SEASON = 3;
```

시즌4 전환은 **env 설정이 아니라 코드 변경 + 배포**다. `/api/gdcup-meta`가 이 값을
`currentSeason`으로 내보내고 gmi-clancup이 그걸 받아 쓰므로, 상수를 4로 올리면
프론트는 자동으로 따라온다(표 복제 없음 — 기존 규칙 그대로).

`gdcup_apps` 실측: 시즌2 16팀 · 시즌3 20팀 · **시즌4 0팀**(신청 전).

### 5-2. 기준 시점 명시 문구 (신청 폼·규정·오버레이 공통)

```
BPI 기준: 2026-09-08 시점 43시즌 최종 전적
(대회일 9/12는 44시즌 3일차라 새 시즌 전적이 없습니다. 44시즌 전적은 반영되지 않습니다.)
```

- **신청 폼**(gdcup-add) · **규정**(gdcup-s4) · **방송 오버레이**(overlay) 세 곳 전부.
- 산정은 **9/2~9/8**에 완료. 9/9 이후에는 `currentSeasonId()`가 44시즌을 가리켜
  **같은 조회가 다른 값을 낸다** — 이게 당일 분쟁의 원인이 된다.

### 5-3. 권고 — 기준 시점을 meta로 내보낸다

문구를 프론트 3곳에 하드코딩하면 갈라진다(구 표 ×1.0 사고와 같은 형태).
`/api/gdcup-meta`에 `bpiAsOf: "2026-09-08"` · `bpiSeason: 43`를 추가하고 세 화면이
받아 쓰는 구조를 권고한다. **구현은 관제탑 승인 후**(GDCUP_* = GmI 소관 대행).
