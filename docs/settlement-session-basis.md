# 정산 엔진 세션 기준 전환 — 설계

> **상태: 발행만. 실행 금지.** 결제 트랙 + 영구 Level 0(정산·DDL).
> 오너 승인 후 착수한다. 이 문서는 착수 시점의 명세이고, 코드는 아직 한 줄도 바뀌지 않았다.
>
> 발행 2026-08-17 · 지시자 관제탑 · 근거는 전부 실DB 실측(스냅 2026-08-17)

## 1. 왜 바꾸는가

지급 귀속의 기준이 저장소 안에 **셋** 존재하고, 엔진은 그중 제일 부정확한 것을 본다.

| 기준 | 위치 | 상태 |
|---|---|---|
| `students.trainer_id` | 학생 1행 = 담당 1명 | **엔진이 보는 값.** 병행수강을 표현할 수 없다 |
| `lesson_enrollments.trainer_id` | 등록(계약) 단위 | 데이터 있음(122행). 장익교 116=준구 / 117=현태 |
| `lesson_sessions.trainer_id` | 세션(실제 진행) 단위 | 데이터 있음(126행). 조회에도 이미 들어와 있다 |

**정본은 세션 기준이다** — 수업을 진행한 트레이너에게 지급하고, 요율도 그쪽 래칫을 쓴다.

발단은 장익교(id 9) 건이다. 담당은 현태인데 7/29·7/30 35판은 준구가 진행했다. 엔진은
`students.trainer_id`만 보므로 그 35판의 발생분이 통째로 현태에게 잡혔다.

`admin-panel.js:356`의 주석이 전환 지점을 정확히 짚고 있다 —
「정산 엔진은 이 필드를 읽지 않으므로(computeStudent는 games·played_at·settled_period만 본다)
추가해도 산출값은 바이트 단위로 같다」. **데이터는 이미 흘러 들어와 있고 엔진만 안 읽는다.**

## 3. ⚠️ 선행 차단 요인 — 지금은 비교 자체가 성립하지 않는다

**같은 하네스에서 준구·현태 둘 다 `gross = 0`이 나온다.**

```
준구  total 526,100  −  paid_out 2,385,300  →  max(0, −1,859,200) = 0
현태  total 619,000  −  paid_out 3,732,600  →  max(0, −3,113,600) = 0
```

`total`과 `paidOut`이 **서로 다른 시간 축**을 세고 있다.

- `total` = 컷오버(2026-07-20) **이후** 미정산 발생분만
- `paidOut` = **역대 전부**의 `payouts.gross` 합 (이월기준 준구 1,606,400 · 현태 1,990,200 포함)

이월기준 행은 컷오버 이전 노동의 대가인데, 그 발생분은 엔진이 애초에 계산하지 않는다
(`CUTOVER` 경계로 제외). 대가만 있고 발생이 없으니 영구 마이너스 잔고가 된다.

설계 의도는 `settled_period` 도장이었다 — 지급한 회차의 세션에 도장을 찍어 `payable`에서
빼는 것. 그런데 **도장이 찍힌 세션은 0건이다**(`settled_period is not null` = 0,
컷오버 이후 세션 72건). 도장이 안 찍히니 발생분은 계속 누적되고, 그 위에 `paidOut`이
전액 누적으로 빠지면서 양쪽 다 0으로 클램프된다.

> **이것이 지시 1-4(전환 전후 비교)의 전제를 깬다.** `gross`로 비교하면 전·후가 모두
> `0 → 0`이라 아무 차이도 안 나온다. 소급 판정은 **`lesson_accrued`(발생분)로 해야 한다.**
> `gross` 비교는 아래 P-0이 해소된 뒤에야 의미가 생긴다.

**P-0 (선행 판정 · 결제 트랙)** — `total`/`paidOut`의 시간 축을 맞추는 방법을 정한다. 셋 중 하나:

1. **이월기준 2행을 `paidOut` 집계에서 제외** — `kind='adjust' and period='이월기준'` 제외.
   가장 작은 변경. 단 6월·7월 monthly 행은 여전히 컷오버 이전분을 일부 포함한다.
2. **`settled_period` 도장을 소급 기입** — 이미 지급된 회차의 세션에 도장을 찍고,
   `paidOut`도 도장이 안 찍힌 회차만 세도록 바꾼다. 설계 의도에 가장 충실하지만 소급 작업이 크다.
3. **`payouts`에 발생 기준월을 명시**하고 `total`과 같은 창(window)으로 필터.

권고는 **2번**이다 — 1·3은 "이번 달 얼마 줄 것인가"를 매번 다시 유도해야 하지만,
2번은 도장이 곧 정산 완료 표식이라 다음 달 계산이 자동으로 닫힌다. 다만 **소급 도장은
Level 0**이고 7월은 이미 `period_locks`로 잠겨 있어 결제 트랙과 잠금 해제 협의가 필요하다.

## 4. 전환 설계

### 4.1 (지시 1-1) `total`·`paidOut` 동시 전환

**핵심 변경: `payable`을 스칼라에서 트레이너별 분해로 바꾼다.**

```js
// 현행
computeStudent(…) -> { payable: N }
computeTrainer:  total = Σ students.filter(x => x.trainer_id === st.id).payable

// 전환 후
computeStudent(…) -> { payable: N, payable_by_trainer: { [trainer_id]: N_t } }   // Σ N_t = N
computeTrainer:  total = Σ students.map(x => x.payable_by_trainer[st.id] || 0)
```

FIFO 루프가 이미 세션 단위로 돌고 각 세션이 `trainer_id`를 들고 있으므로, 누산기 하나를
추가하는 것으로 끝난다(하네스 검증 완료 — `admin-panel.js` 대비 +638자).

```js
let pos = carry;
let accrual = 0, baseNew = 0, bonusNew = 0;
const byTrainer = Object.create(null); let unattributed = 0;   // ← 추가
for (const x of newSess) {
  …
  if (!x.settled_period) {
    const gg = x.trainer_id != null ? (gradsByTrainer[x.trainer_id] || []) : grads;   // ← 4.2
    const r = trainerBaseRateAt(gg, x.played_at);
    const add = baseG * unit * r + bonusG * unit * (r + REPEAT_BONUS);
    accrual += add;
    if (x.trainer_id != null) byTrainer[x.trainer_id] = (byTrainer[x.trainer_id] || 0) + add;
    else unattributed += add;                                   // ← 미귀속 격리(4.5)
  }
  pos += g;
}
```

**`paidOut`은 코드 변경이 없다.** `payouts.staff_id`는 이미 "누가 받았는가"라서 세션 기준과
같은 축이다. 관제탑이 지적한 "한쪽만 바꾸면 A가 재발한다"의 실질은 **배포 순서 제약**이다:

> 세션 기준으로 귀속된 `payouts` 행을 **엔진 전환 전에 먼저 넣으면 안 된다.**
> 발생은 담당 기준(현태)에 있는데 지급만 세션 기준(준구)으로 들어가면, 준구는 발생 없이
> 기지급만 늘어 다음 정산에서 같은 금액이 차감된다 — 준구 47,069원 건이 정확히 이 형태였다.
> **행 INSERT와 엔진 배포는 같은 창에서, 엔진이 먼저다.**

### 4.2 (지시 1-2) 래칫 적용 주체를 세션 `trainer_id`로

호출부에서 `gradByTrainer` 맵 전체를 넘기고, 세션마다 그 세션의 트레이너 래칫을 뽑는다.
`trainerBaseRateAt(grads, asOf)`의 `asOf` 규약(승급 등록일 이후 진행분부터)은 **그대로 둔다** —
소급 방지가 이미 이 함수에 구조적으로 박혀 있다.

호출부 2곳을 함께 고친다: `admin-panel.js:399`(overview) · `admin-panel.js:810`(export.csv).

> ⚠️ `export.csv`(`admin-panel.js:805`)는 `lesson_sessions`를 `select=student_id,games,played_at,
> settled_period,settled_rate`로 읽어 **`trainer_id`가 없다.** overview 경로(`:356`)에만 있다.
> 이 select를 함께 고치지 않으면 CSV만 조용히 구 기준으로 남는다.

### 4.3 (지시 1-3) 재결제 +5%p를 FIFO 귀속 기반으로

현행 경계는 `firstGames`(1차 결제 판수)와 학생 단위 누적 위치 `pos`의 비교다. 세션이 어느
등록을 소진했는지는 보지 않는다. `lesson_sessions.lesson_enrollment_id`(§19e)가 채워지면
경계를 **등록 서수**로 바꾼다.

```
현행:  base 구간 = pos < firstGames           (학생 단위 누적 위치)
전환:  base 구간 = 세션이 귀속된 등록이 그 학생의 1차 등록  (등록 서수)
       보너스 구간 = 2차 이후 등록에 귀속된 세션
```

- **누가 받는가** = 세션의 `trainer_id`
- **base냐 보너스냐** = 세션이 귀속된 **등록의 서수**
- **어느 래칫이냐** = 세션 `trainer_id`의 `graduations`

세 축이 분리되므로 "2차 등록을 새 트레이너가 진행"해도 모순이 없다 — 재결제 보너스는
학생이 다시 샀다는 사실에 붙고, 그 판을 진행한 사람이 받는다.

**D-2 (판정 필요)**: 재결제 경계를 **학생 단위**로 볼 것인가 **(학생×트레이너) 단위**로 볼 것인가.
- 학생 단위(권고) — "재결제 = 학생이 다시 샀다". 위 설계가 이것이다.
- (학생×트레이너) 단위 — 각 트레이너의 첫 등록은 base. 보너스를 트레이너가 벌어들인
  유지 보상으로 읽는 해석. 이 경우 새 트레이너의 첫 블록은 base가 된다.

⚠️ **지금은 판정할 수 없다** — `lesson_sessions.lesson_enrollment_id`가 **126건 전부 null**이다.
7/29·7/30 세션이 등록 116(5/07·준구)을 소진했는지 117(7/15·현태)을 소진했는지 DB에 없다.
**백필(8/18~22) 완료가 이 항목의 착수 조건이다.**

참고로 현행 엔진은 장익교의 컷오버 이후 전량에 **0.70**을 적용한다(하네스 실측 준구분
89,000 = `floor100(127,272 × 0.70)`). 컷오버 이전 진행 76판이 `firstGames`=33을 이미 넘겨
`baseG`가 0으로 떨어지기 때문이다. 이 값이 **옳다는 뜻이 아니라**, 백필 전까지 엔진이
내는 값이 그렇다는 뜻이다.

### 4.4 (판정 필요) `floor100` 분할 지점

`payable = floor100(accrual)`은 현재 학생당 1회다. 트레이너별로 쪼개면 버림도 트레이너별로
일어난다. **하네스 실측 손실 = 전체 1,000원**(1,115,100 → 1,114,100).

- **D-1a (권고)** 트레이너별 `floor100` — 각 지급액이 100원 단위 실송금액과 일치한다. 손실 1,000원.
- **D-1b** 학생 단위로 `floor100` 후 최대 잔여분 트레이너에게 단수 배분 — 총액 보존, 배분 규칙이 늘어난다.

권고는 **1a**다. 코드 주석(`admin-panel.js:236`)이 이미 "세션마다가 아니라 마지막에 한 번만"
으로 반복 버림을 경계하는데, 트레이너당 1회는 실제 송금 건수와 같아서 그 취지를 벗어나지 않는다.

### 4.5 부수 변경

- **미귀속 세션 격리** — `trainer_id`가 null인 세션의 발생분은 어느 트레이너에도 넣지 않고
  `payable_unattributed`로 뺀다(현재 스냅에서는 0건). 담당 기준에서는 학생 담당에게
  조용히 흘러들어갔다. 화면에 노출해 백필 누락을 눈에 보이게 한다.
- **상담 수당 귀속** — `admin-panel.js:393-398`은 상담을 `students.trainer_id`로 귀속한다.
  상담은 세션이 아니라 이 전환의 대상이 아니지만, 같은 컬럼을 쓰므로 **담당 변경 시 함께
  움직인다**는 점을 지시 2 판정에 반영해야 한다.

### 4.6 (관제탑 8/18 지시 4-6) 승급 DM 수신자 기준

승급 DM은 **정산이 아니라 통지**다. 그래서 이 항목만 전환을 기다리지 않고 **먼저 세션 기준으로
구현했다**(2026-08-18). 근거는 두 가지다.

1. **되돌릴 게 없다.** 수신자 선택은 금액을 만들지 않는다. 잘못 보내도 정정 비용은 DM 한 통이고,
   `payments`·`payouts`에 흔적이 남지 않는다. S1~S6 순서 제약(§6.2)의 대상이 아니다.
2. **기다리면 틀린 사람에게 간다.** 담당 기준으로 보내면 장익교 승급 시 DM은 현태에게 가는데
   35판을 진행한 사람은 준구다. 전환 완료까지 몇 주가 걸리는 동안 그 오배송이 매번 반복된다.

**수신자 결정 순서** (`resolvePromoTrainer`, `server.js`):

| 순위 | 기준 | 근거 |
|---|---|---|
| 1 | 최근 90일 실세션(`created_by <> 'seed'`) **최다 진행 트레이너** | 실제로 가르친 사람 = 세션 정본 |
| 2 | 동률이면 **가장 최근 세션**의 트레이너 | 현재 담당에 가깝다 |
| 3 | 실세션이 없으면 **등록(`lesson_enrollments`) 담당** | 계약은 있는데 아직 진행이 없는 경우 |
| 4 | 그것도 없으면 `students.trainer_id` | 최후 폴백(현행 동작과 동일) |

개시잔액(`created_by='seed'`)을 빼는 이유는 §5.1과 같다 — 54행이 한 날짜(7/19)에 몰려 있어
"최다 진행"을 통째로 왜곡한다. 90일 창은 **과거 담당이 현재 담당을 이기는 것**을 막는다
(장익교는 5/07 준구 → 7/15 현태로 등록이 넘어갔고, 창이 없으면 5월 기록이 계속 이긴다).

⚠️ 이 순서는 **정산 귀속과 다를 수 있다.** 정산은 FIFO로 등록에 귀속하지만 통지는 "최근에
가르친 사람"이 맞다. 전환(S4) 이후에도 이 둘을 같은 함수로 합치지 않는다 — 합치면 통지 규칙을
바꾸는 순간 정산이 움직인다.

## 5. (지시 1-4) 전환 전후 비교

### 5.1 판수 귀속 차이 — SQL

금액이 아니라 **판수**를 먼저 본다. FIFO·요율·단가가 개입하지 않아 순수 귀속만 분리된다.

```sql
-- 트레이너별·월별 판수 귀속 차이 (담당 기준 → 세션 기준)
with s as (
  select ls.student_id, ls.trainer_id as sess_tr, u.trainer_id as assigned_tr,
         to_char(ls.played_at,'YYYY-MM') as ym, ls.games
  from lesson_sessions ls
  join students u on u.id = ls.student_id
  where ls.played_at >= '2026-07-20' and ls.games > 0
),
byassigned as (select ym, assigned_tr tr, sum(games) g from s group by 1,2),
bysession  as (select ym, sess_tr     tr, sum(games) g from s group by 1,2)
select coalesce(a.ym,b.ym) as 월, st.name as 트레이너,
       coalesce(a.g,0) as 현행_판, coalesce(b.g,0) as 세션기준_판,
       coalesce(b.g,0) - coalesce(a.g,0) as 차이
from byassigned a
full join bysession b on a.ym = b.ym and a.tr = b.tr
join staff st on st.id = coalesce(a.tr,b.tr)
where coalesce(a.g,0) <> coalesce(b.g,0)
order by 1, 2;
```

### 5.2 금액 차이 — 하네스(실함수)

**금액 비교를 SQL로 재구현하지 않는다.** 단가·FIFO·래칫·`floor100`은 `admin-panel.js`에만
있고, SQL로 옮기면 정본이 둘이 된다 — 이 저장소가 반복해서 당한 사고 형태다
(`GDCUP_WEIGHT_S3` 프론트 복제, FAQ 가격표 중복).

대신 **실함수를 그대로 태운다**. 절차:

1. 실DB 스냅을 PII 제거 형태로 덤프(학생명 → `S{id}`). 엔진이 읽는 컬럼만.
2. `mountAdminPanel(app, deps)`에 가짜 `app`(라우트 캡처) + `sbSelect`(스냅 서빙)를 주입.
3. 전환 전/후 두 벌을 각각 마운트해 `/api/admin/overview`의 `trainers[].lesson_accrued`를 비교.

`gross`가 아니라 **`lesson_accrued`를 비교한다** — §3의 이유로 `gross`는 현재 양쪽 다 0이다.

> 하네스 자체는 세션 스크래치패드에 두고 **저장소에 커밋하지 않는다**(PII 스냅을 동반한다).
> 컷오버 이후 회귀 테스트로 상설화할 때는 합성 데이터로 다시 만든다.

### 5.3 관제탑 제시 수치 대조 (2026-08-18)

| 항목 | 관제탑 | 실측(이 문서) | 판정 |
|---|---|---|---|
| 2026-07 오귀속 판수 | 50판 | **50판** (준구 진행·현태 귀속 35 + 현태 진행·준구 귀속 15 · 6행) | ✅ 일치 |
| 장익교 등록 귀속 | 116=준구 / 117=현태 | **동일** (116 `trainer_id=2` · 117 `trainer_id=5`) | ✅ 일치 |
| 김재성 등록 혼재 | 6건 | **6건** (19·20·21=준구 / 30·31·104=현태) | ✅ 일치 |
| 오귀속 금액 | 182,130원 | 미검증 | ⚠️ 아래 |
| 준구 순차액 | 약 47,000원 | **+66,200** (현태 −67,200) | ⚠️ 아래 |

**금액 두 줄이 어긋나는 이유는 세는 대상이 다르기 때문이다.**

- 182,130원은 **재귀속되는 총액**(50판이 옮겨 다니는 금액)으로 보이고, 66,200원은
  **트레이너별 발생분의 순증감**이다. 양방향(35판 ↔ 15판)이 상쇄되므로 총액 > 순차액은 정상이다.
- 47,069원은 이미 §9 대기 ⑩에 있는 **요율 0.65 가정치**다. 엔진은 같은 구간을 0.70으로 보고
  장익교 준구분을 **89,000**으로 낸다. 즉 47,000 ↔ 66,200 ↔ 89,000의 차이는 귀속이 아니라
  **요율·범위 가정의 차이**다.
- 따라서 **송금액 확정은 시트 7월 산출 내역 대조가 선행**이며(대기 ⑩), 이 문서의 수치로
  `payouts`에 행을 넣지 않는다.

⚠️ 판수는 세 소스가 일치하는데 금액만 갈린다 — 이건 귀속 설계가 아니라 **요율 판정(D-1·P-0)**
문제다. 전환 전후 비교를 금액으로 먼저 하면 이 차이가 전환 탓으로 오독된다.

## 8. 부수 발견 (이 전환과 별개 · 각각 별도 처리)

### 8.1 ⚠️ 음수 정정 세션이 발생분에서 차감되지 않는다

`admin-panel.js:241`의 `if (g <= 0) continue;`가 음수 세션을 **누산 전에 건너뛴다.**
표시용 `newPlayed`는 `sum(newSess, x => x.games)`라 음수를 포함하므로, **표시는 정정을
반영하고 발생분은 반영하지 않는 비대칭**이 생긴다.

| 세션 | 트레이너 | 판수 | 사유 | 미차감액(요율 0.70 가정) |
|---|---|---:|---|---:|
| id 90 · 7/21 · 학생 8 | 준구 | −5 | 오등록 정정(8/2 정산 전) | ≈ 12,800 |
| id 98 · 7/29 · 학생 59 | 준구 | −30 | 중복 등록 보정(대상 세션 #93) | ≈ 80,000 |
| | | | **합계** | **≈ 92,800** |

전액 준구 과다계상이다. 공교롭게 §2.2의 준구 +66,200과 방향이 반대라 부분 상쇄되지만,
**두 건은 무관한 오류**이고 각각 고쳐야 한다. `gross`가 0으로 클램프돼 있어 현재 화면에는
드러나지 않는다.

수정은 `continue`를 걷어내고 음수도 `unit × rate`로 차감하는 것인데, **요율을 어느 시점
것으로 잡을지**(정정 대상 세션의 시점 vs 정정 행의 시점)가 판정 사항이다. 별도 PR.

### 8.2 원천징수 산식 (관제탑 인정 · 별도 PR)

`admin-panel.js:288`의 `Math.round(gross * WITHHOLDING)`(3.3% 일괄 반올림)은 세법과
어긋난다. 정본은 **소득세 3% 원단위절사 + 지방소득세 10% 원단위절사**다.

```
gross 47,069 →  현행 round(47,069 × 0.033) = 1,553
               정본 floor(47,069 × 0.03)/10*10 = 1,410  +  floor(1,410 × 0.1)/10*10 = 140  =  1,550
```

`payouts` 기존 10행은 전부 구 산식이나 `net = gross − withholding` 불변식은 유지하고 있다
(실측 10/10 참). 소급 정정 여부는 오너 판정. **`floor100` 관례는 유지**(관제탑 확정).

### 8.3 `chk_payouts_net_identity` (§19g 발행)

`payouts`에 `net = gross − withholding` CHECK가 없다. `supabase_admin_panel.sql` §19g에
발행했다 — **미실행 · 오너 직접 실행 대기.** 기존 10행이 전부 만족하므로 무중단 추가 가능.
